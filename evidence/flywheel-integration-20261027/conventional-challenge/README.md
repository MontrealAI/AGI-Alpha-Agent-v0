## Frozen scope and results

The 32-case freeze precedes the independent reference and target execution. It contains eight authored
scenario families, four cases each: shared prerequisites with multiple outputs; pending permission
versus documented cost; reachable and unreachable cycles; joint versus separate outputs; binding cost;
binding time; denied permission and lost obligations; exhausted search budgets. The independent
reference was executed and retained before importing the target. This is workstream independence
within one engineering session, not organizational independence or a blinded discovery trial.

Two distinct scenario examples are the shared-fork family, with four checked multi-output plans,
and the cycle-entry family, with two checked plans and two exact no-plan results. They are synthetic
scenario families. They do not satisfy a request for two permission-cleared customer briefs or two
missions through a newly released deployed path.

The conventional solver may use every declared action. It enumerates action subsets and constructs
their lexicographically least executable topological order by repeatedly selecting the least ready
identity. Monotone facts make this greedy ordering complete for an executable subset. It checks all
goals, original obligations, denied permissions and cost/time caps, then minimizes the same tuple:
pending permission count, estimated cost, duration, step sequence. Every action has positive duration;
an unnecessary action cannot improve that tuple. This is a competent ordinary exact construction,
not a weak single published comparator. No execution speed or invention claim is based on its tie.

Both algorithms receive the same inputs, maximum node number and cost/time ceilings. A target
recursive visit and a conventional subset examination are different logical units. Thus these limits
do not establish equal work or a performance advantage. No-plan claims apply only after exhaustive
completion; incomplete results are neither infeasibility nor optimality certificates.

## Preserved harness failure and correction

`RESULTS.json` is the original failed harness receipt. Its 21 independent witness checks initially
failed because the native serialized actions include the inherited `schema_version=1` default and
the frozen action dictionaries omit it. Native `check_access` accepted those same 21 outputs. The
final original harness assertion failed; that failure remains preserved in `ATTEMPT_1_FAILURE.txt`.

`verify_stored.py` adds only this known default to an isolated copy of each input action before the
independent comparison. It checks the already recorded target outputs. It does not execute the target,
change the frozen cases, modify the original results or replace the reference. The resulting
`CORRECTED_VERIFICATION.json` accepts all 21 witnesses and reports the correction explicitly.
No target case was rerun or replaced after seeing its result.

## Operating limits

The instrument reasons over finite supplied monotone facts. It does not verify the truth of a
permission declaration, interpret a policy, authenticate a facility, reserve scarce capacity, model
revocable/time-varying rights, establish physical readiness or execute a scientific experiment.
Plan outputs explicitly grant no authority and claim no customer acceptance. `check_access` verifies
a witness, not global optimality or search completeness. These limits are part of the supported
contract, not defects discovered by this challenge.

A real service would need rights-cleared inputs, actual provider confirmations, contemporaneous
capacity/wait-time evidence, independently agreed acceptance, complete metering and a buyer willing
to pay. Those remain unprovided. This packet supplies narrow engineering evidence to the existing
integration/release owner; it is not a merge, release, deployment or public canary receipt.
