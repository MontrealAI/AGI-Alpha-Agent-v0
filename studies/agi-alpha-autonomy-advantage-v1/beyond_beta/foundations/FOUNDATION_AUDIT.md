# Beyond Beta: foundation and lifecycle audit

## Finding and evidence boundary

The supplied GoalOS foundations support a governed route from work to reusable capability. They do **not** establish that a newly generated skill has additional economic or mission value. BeyondBeta therefore needs two independent gates: evidence that a method satisfies its scoped task contract, and evidence of **net additional mission value over competent current Beta and relevant available capabilities**. Authentication and commitments bind the evidence to an accountable record; they do not make the evidence true.

This review inspected the exact supplied V93 HTML, the exact supplied V97.4 PDF, the supplied GoalOS graph image, and the supplied Alpha image. The V97.4 PDF is byte-identical to the pinned official repository version. Merkle Roots v114, PROOF LOOPS v2, and the organizing Transformational Intelligence manuscript are retained as exact source copies under `beyond_beta/sources/foundations/`. Source identities, inspection methods, and primary links are in [source-provenance.json](source-provenance.json). No price, workload, acceptance estimate, or investment rule from an earlier study is inherited.

### Exact foundation mechanisms

PROOF LOOPS v2 makes the proof level a mission parameter, selected before the outcome. Its L1 through L5 categories distinguish local structure, temporary internal reuse, scoped external review, handoff preparation, and durable formal admission. BeyondBeta should declare its own concrete research policy and evidence basis; using the name L5 does not produce external review. The same-family agreement of several simulated validators is not independent ground truth. The source explicitly proposes failure if admitted capabilities do not improve fresh missions relative to simpler memory alternatives, or if confidence grows faster than evidence. See its “Proof Levels,” “Future Mission Improvement,” and “Evaluation Program” sections.

V97.4 permits a direct eligible `label.agent.agi.eth` controller to write a record under its proposed authority scheme; a nested `x.label.agent.agi.eth` name does not inherit that permission. A record writer, a validator, an admission decision, and execution permission have different responsibilities. The new local implementation may exercise real Ed25519 signature verification and AES-GCM encryption with ephemeral fixture keys while accurately labeling identity, ENS ownership, policy authorization, and evidence as fixtures. It must leave existing `*.club.agi.eth` validation and settlement roles unchanged. See V97.4’s direct-agent authorization, skill commitment, typed attestation, lifecycle, and security sections.

Merkle v114 separates computational state, proof artifacts, commitments, and Chronicle authority. Its leaf profile binds an object class, a schema, and canonical bytes; the tree profile specifies parent ordering, empty-root behavior, odd-leaf behavior, and hash suite. The epoch commitment includes the previous root and policy. Candidate roots may exist for inspection, but they cannot confer future influence. A historical valid inclusion proof cannot override a later revocation. The research adapter should describe its actual profile precisely, including where it differs from the draft’s reference profile. See its “Domain-Separated Leaf Hashing,” “Chronicle-Gated Root Admission,” lifecycle, conformance, and reviewer-workflow sections.

## Executed inspection of V93: concrete failures to prevent

The complete inline script was inspected before execution. [probe_v93_interface.mjs](probe_v93_interface.mjs) evaluates that exact script in a Node VM with no provided filesystem, network, wallet, or browser globals. It replaces rendering/logging/animation functions with no-ops and exposes a read-only state snapshot. Business functions are unchanged; the probes invoke ordinary UI actions and form values. This is a source-logic reproduction, not a browser rendering test, a live exploit, or a security certification.

All nine expected observations reproduced in [v93-interface-probes.json](v93-interface-probes.json): three positive controls and six draft invariant violations.

| Probe | Observed local draft behavior | BeyondBeta invariant |
|---|---|---|
| V93-F01 | `canonicalReview()` promotes a candidate without a Chronicle entry; `reuseSelected()` trusts the resulting status and creates future-prior influence. | Canonical promotion must call the same mandatory admission gate as ordinary admission. No writer or UI route can create an authoritative current record directly. |
| V93-F02 | `retireSelected()` changes current status, but `generateNextMission()` reads the last historical Chronicle entry and uses the retired skill. | Discovery, planning, prompt/context assembly, and dispatch resolve current authority. History is audit material, never an alternate capability index. |
| V93-F03 | Changing the live proof slider admits a candidate originally created under a stricter mission policy. | Evidence, assessment, validation, and admission bind the immutable mission policy version. A policy change is a new evidence/admission epoch. |
| V93-F04 | Repeating admission increases the frontier while the Chronicle entry is deduplicated and no new evidence appears. | Admission is idempotent. Value and capability metrics come from fresh outcomes, not transition counts. |
| V93-F05 | A composite can inherit its parent’s evidence IDs and validator labels and pass after numeric score penalties, without new jobs. | Compositions require their own matched evidence and exact dependency versions. Parent correctness is insufficient for composition correctness or Alpha. |
| V93-F06 | A retired skill can be readmitted using the same evidence through the ordinary admission button. | Terminal records cannot revive. Reinstatement, if the policy permits it, requires an explicit new version and fresh assessment; old history cannot silently regain authority. |

The ordinary good candidate passes its local gate, a clean boot blocks next-mission generation, and the deliberately bad example remains outside Chronicle. These positive controls distinguish specific defects from a harness that rejects or accepts everything. The original supplied file remains unchanged.

## Proposed admission semantics

**Later steering controls the cost boundary.** Paid-job learning is account A, incremental retention is B, and optional separate research is C. The complete-cost requirement below applies to the costs incremental to the claim being tested. Original paid-job learning already charged in A is retained as provenance and enterprise cost; it must not be charged a second time to B/C admission. See [PAID_WORK_FOUNDATION_MAP.md](PAID_WORK_FOUNDATION_MAP.md) for the exact updated interpretation.

For a fixed mission contract, current Beta version, relevant inventory snapshot, and declared finite reuse horizon, compare complete paths on the same fresh case set. The task value function and quality requirements must be fixed before the candidate outcomes are inspected. For path `x`, define its scoped net value as the value of useful accepted outcomes minus execution, correction, verification, integration, support, search, construction, failed research, confirmation, distribution/access, maintenance, revalidation, and risk costs attributable to that path. Unknown material costs are unknown, not zero.

Candidate Alpha is the difference between its scoped net value and each eligible relevant comparator’s net value. Admission requires the declared quality contract and a positive conservative incremental-value criterion. Competent Beta is always included. Existing capabilities are included by a policy-owned relevance rule; the candidate cannot omit a close substitute. The uncertainty rule, case set, value function, allocation horizon, and comparator versions are committed before confirmation. A multiple of a paired standard error on a tiny fixture is only a declared arithmetic gate, not a distribution-free confidence guarantee.

The horizon must have an independently stated useful lifetime and reuse basis. An upper bound on amortization is insufficient if an author can choose whichever number of uses makes a candidate positive. The cost ledger should retain both whole-program value and the prospective decision value of keeping an already acquired asset. In particular, a candidate that has **never** passed full-cost qualification cannot remove its failed build cost by submitting a new record labeled “revalidation.” After genuine initial admission, a later retention decision may appropriately treat already-paid construction as sunk, while the historical lifetime result remains visible and unchanged.

The admission adapter can verify internal arithmetic, object identity, authorized attestations, freshness, and supplied evidence completeness. It cannot infer that arbitrary input booleans describe true correctness. A simulator must supply the explicitly modeled truth and error process; an executed study must supply reproducible task verification. In both cases, evidence carries its basis. “Executed signature” does not turn “simulated outcome” into an observed capability improvement.

### Complementary bundles

A component can be useful only inside a bundle. Do not require every dependency to have individually positive standalone Alpha before testing a joint transformation. Register support artifacts as exact, technically checked dependency records with **no independent future authority**, and qualify the complete composition against Beta and the relevant available compositions. Bind its source versions, allowed use, full combined cost, and fresh composition cases. Discovery should label the qualified bundle and its prerequisites without implying that each prerequisite is independently valuable.

A composition that passes admission must not instantly invalidate its own dependency when its insertion changes a comparison epoch. Distinguish standalone Alpha authority from a support artifact’s explicitly authorized role within a separately admitted bundle. A correctness/security revocation still blocks dependent execution; a historic positive score or retained ciphertext cannot override it.

## Current-state and access rules

The authoritative lookup key includes skill/version, artifact hash, evidence hash, acceptance policy, Beta version, relevant inventory epoch, and dependency versions. Admission rechecks this binding at promotion. Reuse checks it again at authorization **and dispatch**, including expiry, terminal states, caller eligibility, scope, prerequisites, and current grants. A permit created before revocation cannot authorize a later dispatch.

New relevant inventory changes can trigger reassessment of older standalone Alpha claims. An irrelevant addition should not invalidate unrelated scopes. A candidate’s own insertion should not invalidate its newly issued receipt. Relevance is policy-owned and testable. Neither label changes nor old Chronicle history creates a fresh claim. Failed and refused API calls should not mutate authorization state, advance the trusted clock, or consume an unrecorded authority transition.

Define distinct operations for discovery of metadata, retrieval of encrypted material, export of plaintext, execution, and composition. In the primary shared configuration, every direct agent eligible for the scoped execution policy can discover and request use of an admitted shareable capability; the creator cannot maintain an undeclared recipient whitelist. Use remains optional. An execute-only design requires dispatch inside an enforcement boundary. Returning plaintext method IR to an agent is an export even if the function is named `execute`. Revocation can stop subsequent guarded requests; it cannot erase plaintext previously exported to an authorized recipient.

A fixed sanitized IR and allowlisted public provenance are useful bounded controls against accidental client-data sharing. They are not a general confidentiality proof for arbitrary files. More general artifacts would need an explicit review/sanitization policy, charged to the delivery and transfer economics.

## Prospective independent review and remaining integration work

[LIFECYCLE_TEST_SPEC.json](LIFECYCLE_TEST_SPEC.json) specifies positive controls, Alpha/cost failures, promotion bypasses, freshness/revocation, composition, rights, privacy, and shared-availability tests before calibrated outcomes. [graph-review-initial.json](graph-review-initial.json) preserves a source-bound independent probe of the first new graph implementation: it reproduced first-qualification cost erasure through revalidation, same-function composition self-invalidation, and unauthorized-call clock mutation. These were reported to the implementation owner before freeze; later repairs must retain this record and produce a separately named result.

Final acceptance requires the new graph checks to run through the actual simulator/native integration boundary. A well-tested standalone admission object is insufficient if the economic engine changes a productivity multiplier without consulting it, or if an executor dispatches from a stale local cache. All influencing routes must use the current canonical resolver, and graph/discovery/authorization/revalidation costs must appear in the same ledger as production. No economic worlds were run by this review.

The six independently reproduced new-implementation defects were subsequently repaired and independently rechecked in [graph-review-independent-final.json](graph-review-independent-final.json) and [graph-review-additional-independent-final.json](graph-review-additional-independent-final.json): six of six source-bound controls held. Additional maintainer controls cover transitive fresh-case exclusion and separate verifier/admitter identities from the newly supplied Navigator manuscript. These statements describe the named source checkpoints; later source changes require renewed bindings, not retroactive editing of earlier records.

The publication can claim implemented local lifecycle behavior and simulated value only to the extent separately demonstrated. It must not infer additional graph value from admission counts, network benefit from availability alone, or improving invention efficiency from descendant job volume. Those remain separate paired comparisons at equal resources with fresh work and an explicit moving-Beta process.
