# Productive Capital Engine: prospective connected-production protocol

**Study:** agi-alpha-productive-capital-v1, engineering confirmation version 1.
**Scope:** local deterministic research adapters over unmodified source from Alpha main `f836f06e8351e64db1da770e16e304b5feb01f28`. No authenticated executor, operator daemon, remote fleet, model-provider call, chain transaction or live customer engagement is run. No earlier Economics, Foundry or Strategy outcome is reclassified.

## Question and estimands

Does a retained evidence index, followed by a constructed dependency-aware change compiler, preserve acceptance while reducing repeated production work on a connected source-assurance, rollout-planning and bilingual-document workflow? Does it improve over the same ordinary content-cache specialist, and does it expand feasible production under the same bounds? The economic analysis separately tests whether modeled operating surplus can finance specified capability construction and working capital. The human-work comparison remains the primary commercial comparator; these three software arms identify mechanism, not human replacement time.

Primary outcomes are the accepted count for each of three deliverable classes; whole-request CPU and wall time including source hashing, native and portfolio planning, workbench envelopes, independent Python acceptance and persisted artifacts; exact source lines re-examined; parent/child invocations; failure and refusal counts. Family outputs share a joint request cost: never add three copies of the same cost. Neither abstract source-line counts nor a kernel's runtime is complete Agent cost. Human attention, upstream model/engineering costs and service integration costs remain unobserved and are separately modeled.

No universal superiority endpoint is assumed. Any superiority statement must preserve the ordinary cache comparator and all implementation/maintenance costs. Six deterministic project instances cannot establish a population speedup. Report per-project paired results, medians and totals without treating three outputs, repeated cycles or arms as independent tasks. Same-budget frontier expansion is NOT ESTABLISHED unless a predeclared previously unavailable deliverable is accepted with equal cash/human-time/elapsed bounds and strong conventional alternatives fail. A newly exposed interface is not proof of practical impossibility.

## Task selection and inventory

Six projects are generated **after** this protocol, generator, implementation and oracle are hashed. The portfolio is three contexts—SDK release, research publication and operations handoff—crossed with simple (8 source components,6 planning jobs) and complex (14 components,12 jobs) strata. Each yields (a) a source/dependency assurance JSON; (b) a capacity-, precedence-, release- and frozen-start-compliant rollout or repair plan; and (c) a bilingual source-linked HTML dossier. The component bodies are 14 exact public repository source snapshots; project dependency declarations, job labels, durations, capacity and changes are synthetic. These are not six naturally sampled customer engagements or a representative digital-labor market sample.

The generator fixes seeds `2026102500+31*context_index+17*stratum_index` and task structure before confirmation. It generates six fresh base inputs once. All arms see the same component snapshots and requirements. Each arm's repair baseline derives from its own accepted immediately preceding plan. No held-out result is used for selection or retuning. Development uses only `DEV01` with seed1729, retained separately.

Four cycles per project:

1. C0: initial complete production; retain accepted evidence index and verified artifacts.
2. C1: fixed evaluation slice; identical content and task semantics with a new mission revision. Test exact reuse and repeated correctness.
3. C2: fresh slice; change a source body and a planning duration. Construct the fixed child descriptor from the newly computed parent index and accepted predecessor. Child produces a complete transitive invalidation certificate, then only affected cards rebuild.
4. C3: fresh slice; add a dependency edge and reduce future calendar capacity. Preserve starts before observed slot3; repair the actual prior plan. Reuse the constructed child, and record its actual parent call.

Three arms execute in a predeclared cycle-rotated order: full rebuild, flywheel and conventional cache. The ordinary cache uses an independently written iterative dependency-key implementation and provides the same cross-artifact certificate. Both it and the flywheel keep accepted unchanged cards and plans. Full rebuild deliberately reconstructs the complete requested dossier; it is a service alternative, not the strongest reuse comparator. The original Alpha portfolio and corrected native SciPy/HiGHS specialist are available to every arm. Each candidate schedule is independently checked. Equal feasible objectives do not create an invented advantage.

## Capability construction and failures

Parent `evidence-index-v1` binds source bytes, declared dependency edges, source URL and authoritative original-source digest. Child `dependency-repair-v1` uses the parent on every fresh-change execution, computes transitive invalidation, and binds its certificate to the accepted predecessor, child descriptor and revision. This is authored conventional dependency propagation plus fixed-grammar binding, not autonomous discovery of a new algorithm. Child construction timing records binding and validation only; authorship and upstream model interactions are unmetered.

A development candidate `direct-only-v0` is explicitly rejected: it invalidates a changed root but leaves descendants stale. Its failed output and measured qualification costs remain recorded. Pre-freeze implementation failures (relative-path recording and digest-domain/canonical telemetry errors) are retained with exact failed receipts and corrections. Controls include source-provenance-only changes, corrupt parent refusal, cyclic dependency refusal, missing evidence refusal, private-data refusal and supported-size overflow refusal. Controls are reported separately from six legitimate projects.

## Acceptance and budgets

The Python oracle imports neither production compiler nor solver. It independently computes reachability and verifies exact source SHA-256, source URLs, original-source identities, sizes, line counts, declared/transitive dependency sets, complete invalidation and unaffected complement. It independently checks all scheduled jobs, durations, precedence, capacity, release times, frozen starts, makespan, movement and deadline. It verifies exported JSON equality, dossier hash, bilingual headings, every cited source identity, common revision and source keys, and all seven stage records. Custody is common; this is implementation/role separation, not blinded or organizational independence.

Bounds: at most18 source components,18 planning jobs,128 calendar slots,4 crew,2 seconds per native solve,30 seconds per Node subprocess; no paid usage. A finite authored project is normally below these caps. Native failure or absence does not silently remove the strong specialist: its status and rejection are recorded, and the original portfolio remains fallback. No performance threshold is tuned after confirmation. Timing is host-specific; cold process startup is included, native dependency imports are charged once per campaign, and costs of unsupported failed requests remain in the raw log. Persistence/packaging outside a recorded request is separately reported, not silently free.

## Inspectable history and limits

Every mission uses the original `createWorkbench` adapter seam and writes seven stage artifacts: Identify objective/acceptance; Out-Learn pinned evidence; Out-Think affected scope; Out-Design source keys/compiler; Out-Strategise available specialist comparison; Out-Execute five deliverable artifacts; Out-Evolve retained state and actual parent/child digests. Workbench envelope integrity is retained. Source hashes are identity checks, not signatures or new authority. Ordinary local capability records do not confer production authorization.

Unsupported: arbitrary code repair, inferred undeclared dependencies, private data, live publishing, human acceptance, unattended signed remote execution, deployed contract actions, physical rollout and industrial validation. A plan is a plan; a source inventory does not certify contract semantics or security. Commercial demand, collected proceeds, human time and self-financing are not empirical outcomes of this experiment. Negative economics, stronger specialists, missing live operation and no demonstrated acceleration remain publishable conclusions.
