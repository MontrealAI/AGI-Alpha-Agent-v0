## Supported execution seam

The unchanged generic workbench extension is the supported route for the new numerical domain:

```javascript
const workbench = createWorkbench([{manifest, validate, execute}]);
const pack = await workbench.run(spec, {sourceHash, signal, onProgress, onCheckpoint});
const inspection = await workbench.inspectPack(pack);
```

The exact main `examples/successor-workbench/engine.mjs` is byte-identical to released v1.42.0:
SHA-256 `f36f4c3fa45124901755bbb530a8161e98c164f5a66e9b8f932548f5286c93d7`, Git blob
`d3f20b907b4d57867d9a12f46e4c32fb71a03b21`, 26,854 bytes. It commits exact mission input,
source/release, artifacts, costs, Chronicle and the existing seven-package Jobs draft compilation. It has a
60-second per-run ceiling, checkpoint cancellation, strict installed-adapter schema and bounded output files.
Mission data cannot choose an executable, load an arbitrary adapter, change the evaluator or grant authority.

The adapter is source-installed developer code. Its `execute(inputs, checkpoint)` callback must perform the
operation it claims. An already computed numerical report wrapped afterwards is an inspection/publication step,
not evidence that the workbench caused or governed the original computation. An exact subprocess call to fixed
packaged Python code from that callback is a valid local extension; it is not an installed native operator.

Existing `examples/successor-workbench/mission-store.mjs` provides transactional browser history via
`openMissionStore({indexedDB,name})`, `get`, `list`, `save(record,expectedRevision)` and `close`.
It limits history to 12 mission records and 2,000,000 bytes per record, and requires monotone CAS revisions.
Its Git blob is `419875d368a1cfdcbfaa6ac3cb00c2bedda85985`. It stores data, not execution authority.
Use this existing store for the browser when available. The caller still owns source binding, complete cost
accounting, candidate scope and refusal semantics.

### Why the maintained native queue is not silently used for this domain

The new native `CampaignOperation` drives existing `CampaignExperiment`, `DiscoveryLoop`, fixed source selectors
and signed Journal. Its operation examples expose separate search/checking budgets, due-time selection, STOP,
restart reconciliation and immutable submission commitments. It is a **source-clause analysis** operation,
closed to its declared `CampaignUnit`, `SourceDocument`, `SelectionProgram` and installed operator registry.
It is not a generic sparse numerical service. Plugging an unrelated callback into that flow without an eligible
implementation/qualification would invent support that does not exist.

The native workbench similarly invokes a shipped fixed Node worker; it does not accept new arbitrary worker code
through mission JSON. `freeze()` opens retained local role keys, creates an institutional record and registers its
source. Native initialization would create local identity/API credentials and is outside this brief's
no-new-credentials boundary. This audit does not initialize it.

The preserved `backend.agent_scheduler.AgentScheduler` delegates to `AgentManager`. It is a research backend,
not the maintained native queue; exchanging its manager to make a new experiment appear integrated would not
establish native runtime operation. No such substitution is proposed.

The bounded experiment may execute a finite, predeclared recipe through the existing generic workbench and
history seam, with an explicitly labelled foreground research controller. Do not describe that controller as a
new installed scheduler, running hosted service or full native product integration. Browser computation stops
when its tab closes; saved state supports a later explicit resume. Python/Node computation exists only while its
local process is running. An authenticated approved-executor mode remains disconnected unless separately observed.
