# Independent experiment review: Software Capability Foundry

Reviewer role: a separate assistant agent, not an independent laboratory or human audit. This document is prospective. No confirmation tasks have been generated, executed, or inspected by this reviewer.

## The scientific boundary

The useful contribution can be a real, correctness-preserving engineering instrument plus a prospective causal study of reuse. A faster patch alone cannot establish either capability inheritance or an improved improvement process. A predetermined script that serves a known optimization is not evidence of an autonomous agent discovering that optimization.

Separate the following estimands before freezing:

1. **Service utility:** change in total cost of obtaining one correct useful output versus the strongest practical direct method.
2. **Transfer utility:** change in total cost of obtaining an output on a fresh instance when the retained executable asset is available, versus a capable alternative allowed to reconstruct it.
3. **Construction utility:** change in total cost of constructing and qualifying a distinct later capability with versus without the earlier asset.
4. **Investment payoff:** whether the complete incremental discovery, unsuccessful-candidate, construction, qualification, integration and maintenance investment is recovered at a stated recurrence workload.
5. **Feedback:** whether a measured, actually usable resource saving was assigned to a bounded further task and what that task delivered.

Compounding requires a useful capability to contribute to a further useful capability. Acceleration additionally requires evidence that the rate of improvement increases. Do not infer either from the cumulative number of runs.

## Candidate selection gate

Select at most three candidate bottlenecks from pinned production source. For each record exact source paths and commits, the recurring call site, its actual semantics and correctness oracle, supported environments, observed development cost, and the evidence of recurrence. Preserve rejected candidates and reasons.

Prefer a bounded local bottleneck that can be reproduced from public repository inputs. An honest microbenchmark is better than attributing uncontrolled historical CI differences to the proposed method. State explicitly when generated scaling inputs extend an observed source pattern rather than represent measured production demand.

Artifact verification has a particularly important boundary: an mtime/size cache is not a substitute for required cryptographic verification. A speedup that omits fresh hashing or required release checks is ineligible. Within-operation deduplication must preserve the specified snapshot, race, path, signature, error and failure semantics.

## Minimum comparator matrix

| Arm | What it receives | What it tests |
| --- | --- | --- |
| Existing production implementation | Exact pinned source and supported inputs | Practical first-delivery improvement |
| Strong direct specialist | Mature implementation, profiling, batching/vectorization where legitimate, all public information | Whether the proposed method beats the best feasible direct engineering solution |
| Same controller without the retained asset | Same public information, tools, budget, and permitted reconstruction | Incremental value of ready executable content |
| Ordinary saved tooling/history/cache | Legitimate saved code, documentation and cache with identical invalidation rules | Whether the claim is merely conventional reuse |
| Equally funded conventional reusable-tool system | Same development instances, resource limits, retention opportunities and admission rules | Whether the proposed process adds value over ordinary tool engineering |
| Proposed capability process | Parent executable, provenance, limits and qualification evidence | Candidate mechanism |
| Independently equivalent asset | Independently implemented equivalent content with its construction cost recorded | Content value versus ancestry label |

No-parent reconstruction and equivalent-content arms are mandatory for any inheritance claim. A static arm that deliberately executes a slower algorithm is not an equally capable agent. If actual agent/model comparisons cannot be executed, label the study as deterministic engineering and withhold the agent-level hypothesis.

All arms may retain the strongest incumbent, abstain, and use mature specialists. Compare total pipelines, not only the kernel that favors the proposed method. Maintain separate service and improvement budgets. Charge failures and unused construction to improvement cost.

## Four visible missions

- **A — deliver:** reproduce a pinned bottleneck, diagnose it, obtain a verified improvement, and preserve a versioned executable parent instrument. The improvement must remain useful if no later mission occurs.
- **B — transfer:** use changed real inputs or structure, invoke the accepted parent bytes, and record how investigation, construction or verification changed. Ordinary repeat execution on a renamed input is insufficient.
- **C — construct:** use the accepted parent to construct or qualify a distinct later capability with a different interface or outcome. Record a content hash of the accepted parent, the exact invocation and returned data consumed by the child builder, the child source bytes, the independent qualification, and the final served child invocation.
- **D — boundary:** present an out-of-scope case. Demonstrate a correct refusal, fallback or retirement without incorrectly accepting stale or invalid evidence. Include an ordinary alternative that can complete the task where possible.

Choose these cases prospectively from development evidence. They are explanatory cases, never counted again as protected confirmation.

## Protected confirmation

Freeze source, dependency versions, environment, task-generation rules or task list, source snapshot hashes, all comparators, budgets, correctness gate, effect threshold, statistical unit, analysis code and stopping rule. Record a timestamped hash before generating fresh task seeds.

The evaluator and fresh task generator are separate from candidate code. Candidate code receives task inputs only. It cannot edit final evaluator files, acceptance thresholds or protected cases. Any evaluator correction requires its own review, version, reason and new evidence boundary; retain the original outputs.

Use independent repository or mission instances as units. A suggested bounded design is 24 or more independently generated repository instances, each evaluated by every arm, with cold and warm process conditions reported separately and randomized/interleaved arm order within each block. Repeated timings of one instance are subsamples, not additional independent trials. If task generation shares a small number of source repositories, report the limited cross-repository generalization.

Generate confirmation seeds only after the freeze. Run confirmation once. Do not tune on confirmation results, replace unfavorable cases, rerun until favorable or drop failed/slow runs. Include timeouts and incorrect outputs in the all-attempt accounting. A result-dependent second confirmation is a new study, not a continuation of the same holdout.

For timing use monotonic wall time and process CPU separately. Specify process startup, input staging, disk state, caches and verification inclusion. An unprivileged disposable host cannot promise an OS-cold disk cache; call this a fresh-process condition unless actual cache eviction is verified. Record runtime, hardware, affinity if controlled, environment variability and run order.

## Correctness gate and adversarial cases

Correctness precedes speed. Compare exact required outputs and failure categories to an independently implemented oracle, then include property and adversarial cases chosen from the actual contract.

For file/artifact workflows, consider empty files, duplicate entries, duplicate content at different paths, order independence, non-ASCII names, case sensitivity, huge or sparse files where supported, symlinks, path traversal, missing files, changed files, malformed records, wrong expected digests, truncated reads, interrupted writes, stale manifests, partial outputs, repeated runs, clean builds and recovery. Do not claim races or unsupported platforms tested if they were not exercised.

Rollback must restore an accepted prior implementation or perform a safe refusal. STOP must prevent further work or publication and preserve enough checkpoint state for documented recovery. A browser STOP animation alone is insufficient evidence of executor cancellation.

Any missed required defect is a correctness failure, not a timing observation to average away. A limited zero-failure sample bounds risk only under its sampling assumptions; it does not establish universal correctness.

## Proposed admission decisions

Predeclare a nontrivial effect threshold informed by development measurements, for example at least a 5% reduction in total measured mission cost versus the strongest practical arm. If using a percentage threshold, define whether it applies to paired geometric means, medians or sums before confirmation.

For a timing claim, report a paired interval at the independent-instance level and require its lower confidence bound to exceed the predeclared threshold. Report all arms and both favorable and unfavorable conditions. A cluster bootstrap or a paired randomization analysis can be appropriate; neither turns a narrow generated family into evidence of broad AGI.

Use distinct decisions:

- **Correctness:** accepted, failed, or unsupported.
- **Next-use admission:** the asset is worth using on a specified next mission under a specified cost model.
- **Research payoff:** complete known investment recovered, not recovered, or indeterminate because material costs are unknown.
- **Process claim:** improvement discovery/qualification benefits demonstrated, failed, or not tested.

Strong specialist ties are a valuable boundary result. Do not award a win for an ancestry label when equivalent content performs equally well.

## Complete cost and feedback ledger

Record attempted candidates, code construction and review, profiling, model calls where observable, all executions, correctness checks, integration, storage, retrieval, maintenance, retries and operator time. Mark unmeasured model and human costs unknown; do not enter zero. Distinguish abstract operation counts, CPU seconds, elapsed seconds, memory, disk bytes, runner minutes and currency.

For known recurring per-use saving `s` and known incremental fixed investment `I`, report `ceil(I/s)` only when the units match and `s > 0`. Show sensitivity to recurrence, maintenance and uncertainty. CPU savings are not automatically cash savings or usable wall time. Free GitHub minutes are not paid cash savings.

To test feedback, allocate only measured usable freed capacity to a bounded child task. External research allocation must be separately labeled. If a saving exists only as a counterfactual benchmark estimate, do not say it financed the child. Report a resource ledger and what the bounded child task actually completed.

## Integration and claims

Keep the research controller explicitly separate from production scheduling. Use the existing mission/history/verification interface only where its exact supported schema and execution authority are observed. A generated unsigned work order, simulated settlement or inspected contract is not live Jobs/Fleet/token utility.

The browser must label local computation, recorded experiment replay and approved connected execution separately. No-account example should execute a real bounded operation locally. Downloadable evidence must distinguish observed results from hypothetical recurrence calculations.

Final manuscript must state whether independent owners reviewed the patch, whether a PR exists, whether it merged, whether it deployed and whether public access was verified. These are separate statuses.

## Review stop conditions

Withhold primary causal acceptance if comparators are artificially weakened, only the retained arm has useful public code, fixed overhead is hidden, protected cases were inspected and tuned, the selected child never invokes the parent, correctness checks are dropped, synthetic workloads are described as production demand, or unknown cost is converted to profit.

Complete and publish the negative or limited finding with its evidence if the primary gate fails. Propose one next falsifiable change; do not start an unlimited search for success.

## Concrete selection: bounded exact Git snapshot reading

The selected development source is `scripts/strategy_engineering_release.py::_committed_files` at Alpha commit `f836f06e8351e64db1da770e16e304b5feb01f28`. Its per-file `git show --no-textconv` calls provide a direct reproducible process-launch bottleneck. `scripts/paper_changes.py::blob` separately illustrates repeated exact-object size/body retrieval. These call sites establish a recurring operation pattern; they do not establish its annual production workload or commercial value.

The concrete parent is an exact-commit reader that retains path/mode, file-count, per-file, total-byte and object-content checks while batching Git object retrieval. The distinct proposed child diagnoses archive-versus-commit drift. Its usefulness must be tested against a direct archive verifier as well as a no-parent reconstruction. Neither component skips final release acceptance.

Development warning: the original Strategy reader accepts modes `100644` and `100755`; the paper-only proof permits only `100644`. A general reader cannot silently widen the latter policy. Preserve each caller's mode restriction at its own boundary. Do not treat supported-input expansion as a verified performance improvement.

The independent comparator in `specialist.py` was authored before inspecting candidate code. It directly uses native Git tree and batch operations, checks SHA-1 object identities, and does no persistent caching. It is evidence that equivalent useful content need not inherit the candidate's lineage. SHA-1 here checks consistency with this repository's native Git object format; it is not a new authenticity guarantee, signature substitute or claim of collision resistance beyond Git's format.

The planned confirmation family consists of controlled, fresh repository instances derived from pinned public source bytes, with changed directory structures and inventory sizes. These are independent generated instances conditional on a shared generator and source ecosystem, not a sample of independent real-world repositories. Generalization is therefore to that generated family only. A file-reader microbenchmark does not on its own establish agent-level learning or an improved autonomous discovery process.

Because all readers consume immutable commit objects, the relevant warm condition is repeated process/application state with likely OS page-cache warmth. No digest cache of mutable working-tree files is needed or authorized. No claim of actual OS-cold disk timing is justified without verified cache control.
