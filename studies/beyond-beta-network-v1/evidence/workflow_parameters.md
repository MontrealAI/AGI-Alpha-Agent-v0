# Automated workflow module: parameter and accounting contract

Module: `studies/beyond-beta-network-v1/model/workflow.mjs`.

The module is an economic/workflow simulation, not live frontier execution or an implementation of AlphaEvolve. Current official model configurations and prices are reported evidence. Every usage budget, latency, failure probability, correction rate, screening effect, and asset gain is **assumed or explored**. The module exposes defaults; the new study's frozen scenario file must record any overrides.

## Public interface

`planJob(config, job, capabilities, rng)` takes a stable keyed `rng(label)` returning a value in [0,1). Job fields are `id`, `complexity`, `scopeSupported`, and optionally a candidate-count override. Normalized capability flags are `representation`, `certificate`, `experiment`, and a reserved unused `recourse` flag. Calls in paired arms must use the same job ID and keyed uncertainty; do not use an arm-specific seed.

The return has integer-cent cost details, role token usage, total input partitions and output, automated service occupancy, solver search CPU-hours, validator CPU-hours, and total CPU-hours. It also returns a blind upper reservation, outcome status and diagnostics. **Cash/capacity admission must use only reserved fields; no admission decision may inspect eventual correctness, fitness, retry count, or failure.**

`reserveJob` never calls the random generator or reads an outcome. It reserves the maximum permitted attempts and recovery. Rounding occurs on the same role-call units as actual accounting, so reservation cannot be short by fractional-cent accumulation. Aggregate role work is assumed split into requests no larger than 200k input and128k output tokens; individual requests therefore avoid the >272k input premium. This orchestration assumption must remain visible.

Deterministic reservations are memoized exactly in a bounded4096-entry cache. The key includes normalized configuration, supported scope, complexity/candidate budget and effective capability flags. Config-object snapshots invalidate a cached fingerprint when a primitive field changes. Returned reservations are deeply immutable; unsupported complex configuration objects bypass the cache. `reserveJobUncached` calls the same arithmetic implementation for equality controls. No stochastic workflow, quality draw, buyer outcome or scientific result is cached or approximated.

`planCampaignReview` performs a separate campaign with a 96-case maximum by default. It can stop after an observed falsifying test. A campaign's latent invalidity is sampled once; it is not a new independent 5% invalidity event on every case. A valid candidate does not become invalid merely because more tests were run. The review does not generate a new algorithm and cannot itself demonstrate faster invention.

`planAuxiliary(config, kind, {scale})` prices pre-contract qualification, investment evaluation, transfer adaptation, recurring revalidation, maintenance and recovery. These deterministic plans expose all token/CPU/service use and exact reservation aliases; they do not assert that a validation passed. The enterprise must book their resource flow, even when their service occupancy is too small to justify a whole delivery slot. Pre-contract qualification uses25k Astra input/4k output per unit; post-contract formalization uses the distinct100k/16k job-intake budget.

`planConstruction(config, {workUnits, keys})` converts a declared workload into a tariff-backed construction ledger. Work units are not dollars. The default unit contains5000 Astra input tokens,900 total output tokens and1.2 aggregate CPU-hours. `assetConstructionMultiplier` scales base units once; token and compute multipliers independently scale their resource categories. The full token count is partitioned among hypothesis design, candidate construction, failed-design correction, critique, migration/integration and internal revalidation. The separate final held-out review is not included. Tools, orchestration sessions and storage are also charged explicitly. There is no unexplained residual allowance or contingency expense. Construction service occupancy is the larger of the declared occupied-time floor and modeled token processing time; solver CPU is accounted separately in the resource-flow schedule.

For example,3600 work units imply18M input tokens,3.24M output tokens and4320CPU-hours before multipliers. With the study's provisional USD0.0493704 per configured compute-resource hour, the exact constructor returns USD534.96 including its tools/storage but excluding independent final review. The corresponding4900-unit and8500-unit workloads return USD728.21 and USD1263.14. These are tariff arithmetic on assumed workloads, not measurements of research sufficiency or evidence that those workloads will discover a useful capability. The benchmark must preserve unsuccessful construction campaigns at their full modeled cost.

## Baseline work and role accounting

Each supported job receives automated intake and a semantic critic. It considers12 candidates times the known complexity factor per attempt, with at most two additional attempts. Every candidate incurs Astra Pro max generation, Astra Pro max critique, Terra max execution, search compute and machine validation. Correction and revalidation receive their own Astra Pro max budgets. Final evaluation and packaging are charged; observed failure/no-improvement handling receives recovery work. An undetected error does not trigger clairvoyant recovery. A later observed incident must be charged by the enterprise model at that later time.

The default candidate budget is100k Astra input/20k total output,40k/5k for critique, and20k/3k Terra input/output for execution. Output includes reasoning and all aggregated Pro work; the simulator does not apply an extra Pro multiplier. Cached-read and30-minute cache-write assumptions are20% and5% of input, respectively, with disjoint accounting. The remaining input pays the ordinary tariff. `ROLE_BUDGETS` exposes the other stage budgets in full.

`paidJobCostComponents(plan)` classifies this already charged customer cost (A) into problem formulation, candidate construction/learning, verification/revalidation, packaging/recovery, and compute/tools/storage. It reconciles to the exact integer-cent job ledger and adds no expense. Producer search, criticism, executable candidate tests and failed corrections are substantive modeled work on the customer's problem. They may leave a candidate method worth retaining; they do not guarantee transferable Alpha. Remaining extraction/generalization, integration, network validation/distribution and upkeep are separately charged incremental retention costs (B). Optional research beyond the paid task is a separate cost (C). Original paid-job search is not charged again when deciding whether to retain its result.

The default20 search CPU-hours and0.2 validation CPU-hours per candidate are computational workload assumptions. A final independent validation adds0.5 CPU-hours times complexity. The chosen USD0.12/CPU-hour needs a separate matching provider/resource calibration; it is not an OpenAI token or container tariff. API sandbox charges are for orchestration sessions, separate from that external solver compute. Default storage and tool-call counts are explicit assumptions. Model service occupancy includes assumed token throughput and evaluation CPU work divided by assumed eight-way evaluation parallelism; this ratio is not a documented API entitlement.

## Quality and correlation

`initialError` controls mechanically defective generated candidates and a smaller initial semantic-error component. `commonError` is a campaign-level shared interpretation failure. It persists across the producer, critic and retries, so repeated model agreement cannot eliminate it. Nonshared semantic errors can be noticed by the semantic check and corrected. Mechanical defects are checked separately with `mechanicalDetection`; certificate availability does not automatically prove the semantic charter.

`improvementProbability` is a per-candidate hypothesis, distinct from validity and customer acceptance. A candidate is selected using an observed pass and claimed improvement; selection never uses its latent true validity. A false pass can therefore be selected. If search finds no improvement, the permitted competent known solver remains available. The enterprise must explicitly decide whether such a feasible baseline result meets the offered contract; an improvement-only contract cannot be billed as successful just because the fallback is feasible.

The module returns `correct`, `feasible`, `improved`, `abstained`, `invalid_pass` and `no_improvement` distinctions. Truth is used for simulated downstream outcome measurement, not for pre-execution investment or admission decisions. These probabilities are not calibrated from vendor benchmarks.

## Asset effects

Competent Beta can ignore an unhelpful isolated representation A or certificate/search adapter B; the Beyond Beta model therefore imposes no single-component overhead. A+B applies an assumed0.75 stage resource factor on standard jobs or0.40 on more complex jobs before scenario overrides. The interpolation parameter `bundleResourceEffect=0` is the no-gain case. These factors affect candidate reconstruction, search, and validation resources only. They do not change the frontier model or inject a general quality gain. Scope and effectiveness remain empirical hypotheses, and the enterprise must account for acquisition failures, overlap, maintenance and invalidation separately.

The study's alias `bundleEffect` sets the complex-job resource factor, and linearly maps its savings to the standard-job factor:0.40 maps to0.75 and1 maps to1. Supplied study aliases take precedence, including when the caller spreads the module defaults first. Therefore the study's factor1 sensitivity is a real null in every job class. Legacy single-component-overhead fields are accepted as input for compatibility but do not penalize a competent baseline in this study.

All arms already use an ordinary cheap mechanical screen. Default baseline sensitivity is0.65; a family-specific experiment asset adds0.15 before Beta absorption. The experiment asset changes only this preliminary test. CPU is saved only on candidates that test actually rejects. Valid candidates can be incorrectly screened out with the same assumed0.01 false-positive probability in all arms. Valid candidates that pass the screen receive no blanket CPU discount. This provides an explicit mechanism and a cost for mistaken screening.

`betaResourceFactor` scales all model token work and search compute for substantive job, construction and review plans passed the current Beta configuration, in both paired arms; validator compute remains independently counted. Fixed ancillary plans constructed from the original configuration retain their legacy integration budgets as a conservative accounting assumption. This distinction does not assert that an actual future model improves every role uniformly. `betaBundleAbsorption` moves resource and certificate advantages toward Beta, with exact null at full absorption. `betaExperimentAbsorption` separately moves family-screen coverage into the common baseline and removes its incremental retained value; if omitted it defaults to bundle absorption. A future Beta upgrade is a scenario assumption, not a claimed future release or a change to verified current tariffs. Both baseline and retained arms receive every modeled upgrade.

No baseline is forbidden from using known solvers or reconstructing equivalent methods. The enterprise model must not convert absent asset metadata into absent frontier competence. Any stronger claim about cheaper subsequent capability invention requires matched fresh construction campaigns beyond this delivery module.

## Controls already run

The small synthetic controls in `workflow.test.mjs` check cent-level addition, disjoint input partitioning, the resource-only bundle effect, real zero-gain and fully absorbed cases, no penalty for ignoring unhelpful singles, no clairvoyant abstention/recovery, bounded retries, known-solver fallback, actual-invalid-candidate screening savings, unsupported-scope refusal, reservation bounds across all three complexity classes and several resource stresses, early stopping of a falsified held-out review, auxiliary-stage budgets, exact construction allocations and independent scaling of tokens/compute. Gate/probe tests additionally check full paid evaluation costs, fresh evidence, cluster dependence, exact-null rejection and absence of latent truth from admission logic. They use no primary economic outcome seeds and make no claim about actual frontier performance.
