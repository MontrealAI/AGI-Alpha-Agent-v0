# Manual incumbent: confirmation execution protocol

**Status:** operational documentation only, written before the primary source/protocol freeze, after the incumbent inventory and conventional development freeze, without inspecting primary inputs or outcomes. It does not change the frozen selection, common 61-case contract, verifier, resource limits or acceptance criterion. Six already selected fresh missions are evaluated; this document does not select replacements.

## What arm A represents

Arm A is the **researcher-assisted completion workflow observed in this study**, with the retained assets in `protocol/incumbent-inventory.json`. It is not a pre-existing production service, a recruited human panel or a human-without-AI benchmark. Root acts as the researcher/operator; assistant inference and tool use must remain visible.

Retain the original probe, measured launcher, independent verifier, environment preparation, first-delivery assembly script, saved commands, source reports, ordinary tools, source/wheel assets and prepared environments. Keep all applicable pre-freeze corrections, including the original FastAPI import bridge and the distinction between a current native lock and a deployed production lock. Historical artifacts remain unchanged. The eight inventoried file identities were checked against their frozen hashes while preparing this document; all matched.

The comparison is **complete accepted assessment against complete accepted assessment**. A verified rejection of a proposed refresh can be a useful accepted assessment. Source-only v1 remains a narrower coverage-gap reference; its cheap incomplete output is never an equivalent accepted deliverable.

## Preserve efficient reuse without inventing a new decision producer

Root may reuse shell history, argument-generation snippets, source templates, hash/manifest utilities and ordinary parameterization. Do not require retyping, repeated environment preparation, cold caches or manual arithmetic merely to enlarge an apparent improvement. Charge any ordinary adaptation once and retain it for all six missions.

The saved `curation/assemble_first_delivery.py` is a legitimate incumbent asset, but it hardcodes development paths, mission metadata, version prose, 61/61 counts and a preserved-only branch. Do not execute those assumptions unchanged on new evidence. Preserve its original hash; record the per-mission path/metadata bindings and any derived copy or edit. Use the actual verified counts, versions and outcome, and update both languages. Routine parameterization may be prepared before outcomes and reused; it is not free construction.

The distinguishing observed operation is root's explicit finalization and review of each packet using these retained tools. Do not introduce B's new automated decision producer into A and describe the resulting run as the unchanged incumbent. Conversely, do not prohibit reasonable scripting merely because B also automates it. If root constructs a new durable decision producer beyond ordinary parameterization, record the added capability, construction and exposure; report it as an upgraded baseline or secondary experiment instead of silently attributing it to frozen A.

1. **Open a new execution record before work.** Record mission/job digest, role, substantive trigger, current asset hashes, prepared environment/lock identities and the beginning timestamp. Use the same consumer source, contract, packages, permissions and declared bounds as B/C. Record cache state and any setup work; an unchanged request is a no-op/replay, not a new mission.

Allow two workers, as in B/C. Each is wrapped by `measured_run.py` with the same time/resource limits and pre/post bindings for worker, contract, projection profile, source, lock, preparation manifest and interpreter. 3. **Run the same independent component verifier.** Bind each observation to its matching environment preparation, contract, original-import projection and consumer. Distinguish actual timeout/launch/missing-output failures from an executed negative result. 4. **Finalize the complete packet with the incumbent assets.** Root reads A's own exact verifier records, reuses the saved assembly/template work, checks source/environment/receipt bindings and supplies the justified bounded action. Include all required observations, verification, reproducible commands, source/projection/case identity, resource receipts, limitations, remaining application qualification and English/French readable output. Never copy a positive development verdict or another arm's packet into A.
5. **Apply common independent package acceptance.** An independent checker/reviewer applies the same complete-outcome rules used for B/C, including custody, exact identities, complete required cases, correct decision, readable action, patch and reproducibility. Material criticism must cite the relevant evidence, discrepancy and consequence; independent verification adjudicates it before correction. Preserve rejected editions and correction costs. Finish the end-to-end record only when a complete assessment is accepted or the bounded attempt is finally incomplete.

Use the frozen processing envelope and correction allowance. This document does not create a more generous deadline or a new resource cap. If a bound is exceeded, record it under the existing rule. Shared launch/metering conveniences are permissible only as measurement infrastructure; disclose their use and charge their common construction consistently. Root may use a single orchestration tool call to start both ordinary commands; that is not a customer-time measurement or a new automatic verdict.

## Decision rules and complete acceptance

| Evidence | Correct bounded assessment |
|---|---|
| Baseline and proposed profile both satisfy every required case with complete custody | Accept the finite component evidence for further qualification; keep the current native lock pending remaining application/release gates |
| Baseline satisfies the contract; proposed profile has attributable, complete verified mismatches | Reject/hold this proposed component refresh, retain the verified baseline and provide the exact reproduction |
| Missing, stale, unexecuted, mistyped or unresolved required evidence; failed source/environment/receipt binding | Incomplete/HOLD; no positive component conclusion |
| Baseline itself does not satisfy the contract | Investigate the baseline/requirement relationship; do not attribute the discrepancy to the proposed dependency change without supporting evidence |

The preserved-only development assembler must not force a negative assessment into a positive template. Root can finalize the appropriate record using its existing source and manifest utilities; retain that observed work. Complete assessment acceptance is distinct from the proposed profile passing, customer acceptance, release authorization and paid demand.

## Measurement and accounting

For each mission record observed actions and their artifacts: metadata/path binding, process launch, verifier invocation, packet assembly, inspection, criticism, adjudication and correction. Label these as researcher/assistant actions, not human labor minutes. Record whether a script, saved command or cache supplied each step. Record actual ordering and cross-arm exposure; if root has seen B/C outcomes, disclose it and make no blinded-human-accuracy claim.

Measure wall-clock service span from A's first mission action through its final accepted packet, including waiting, assembly, verification and corrections. Also retain the bounded mechanical probe/verification interval so scheduling gaps can be understood. Record process CPU, storage/output bytes, setup/download quantities, retries, failures and remaining customer tasks. Do not sum nested inclusive process receipts twice; use an outer aggregate or clearly disjoint component totals. Concurrent before/after durations are not added to estimate elapsed turnaround.

Separate common pre-freeze construction, A-specific parameterization/adaptation, marginal execution, recurring maintenance and residual exceptions. Shared environments and verifier construction receive the same declared allocation policy across arms. Root's elapsed chat time is neither a wage bill nor an inference bill. Unmeasured attention minutes, inference tokens/dollars, maintenance price, customer price and customer savings remain unknown.

## Interpretation

Six changed registered inputs yield at most six substantive assessments per arm; 61 cases, before/after environments, repairs, repeated verification and timing reruns do not add missions. A failed or incomplete attempt remains in the denominator and cost record. No outcome-dependent replacement is introduced here.

The primary comparison may establish complete useful automation, fewer observed orchestration actions, better reliability or measured execution differences. It cannot infer attention savings, commercial superiority or investment payback from unknown minutes, zero-price attention, assistant elapsed time or available accounting allocations. If equally capable conventional reuse matches B, retain the useful conventional component and report the tie. If A already performs the task well with its retained assets, that is evidence about the actual investment opportunity, not a reason to weaken A.
