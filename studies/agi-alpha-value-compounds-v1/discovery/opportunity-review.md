## Recommendation

The most promising complementary contribution is an **actionable release/change dossier**, built by composing existing source-bound reports and validators. Its useful deliverable should tell an integration owner: what changed; which existing evidence still describes the changed source; which required evidence is absent, stale, failed or explicitly unqualified; and which exact action or owner decision is needed next. It must be downloadable, source-pinned and reproducible. This is read-only release assessment, not repair-admission or validation-performance research.

The case for usefulness is stronger than the case for economic payback. The actual project maintains separate source, browser, installed-runtime, CI, package, publication and approved-operator evidence. `RELEASE_READINESS.md` explicitly says source notes and earlier local checks do not qualify a new source. `wait_for_release_ci.py` binds workflow and job evidence to exact SHA, main branch, push event, latest run and run attempt; a green paper workflow cannot replace full software qualification. A dossier can expose these distinctions before an operator attempts the wrong next step. No observed paid demand, human-duration measurement or positive lower bound on cash savings is established by this inspection.

The narrowly reusable asset should be an extraction and reconciliation recipe for existing evidence schemas, not a second release engine. It should report `unknown` when a required record is unavailable. The existing validators remain authoritative. A report must never set a failed or missing gate to pass, infer operator authority, issue a release, or reuse prior results across a source change without existing policy support.

## Protocol advice

Define an accepted dossier before choosing a title or reading confirmation outcomes. Minimum outputs: exact source revision and comparison base; complete declared requirement inventory; source URLs and content identities; status per requirement (`satisfied`, `failed`, `missing`, `stale`, `out-of-scope`, `unknown`); specific next action; explicit local/CI/approved-operator/production scope; machine-readable evidence links and a concise human report. A dossier should never be called a release authorization.

Count a new mission only when substantive input evidence or requirements change. Multiple assertions, files, methods, retries and timed repeats remain observations within that mission. A repeated unchanged request should return the existing dossier or a no-op receipt. The same defect remaining across commits is one defect family even if several changed-source assessments are legitimate missions.

Use three arms:

1. Existing native audit/release scripts and ordinary Git/GitHub tools, retaining all current caches and reusable scripts. This is the actual incumbent, not manual reconstruction of already automated functionality.
2. The same path plus the retained reconciliation capability. Charge acquisition, parsing, reporting, independent validation and integration; a complete dossier's cost matters, not a tiny helper's time.
3. An equally permitted conventional builder that may write a simple JSON/SQL/jq or Python reconciliation script and retain it. Charge its construction and upkeep as well. Similar or identical output/cost is not an algorithmic breakthrough; it can still support conventional automation's usefulness.

Reserve confirmation on source histories or evidence updates not inspected by any constructor, with the exposure rule specified in advance. Fetching all current revisions during discovery makes them exposed. If only historical unseen-by-constructor cases are available, call them a temporally historical held-out evaluation, not prospective field recurrence. A future commit is not an independent defect family by itself. Freeze exact acceptance criteria, methods and failure accounting before obtaining outcome-bearing confirmation artifacts.

Independent validation should consume raw source evidence and check report statements against native validators, not trust the report generator's own verdict. Negative controls can alter source SHA, run attempt, event, missing requirement, failed security result or operator scope. They are adversarial controls, not additional jobs or observed field failures.

## Economic interpretation

The useful novelty is potential **coverage of a previously missing decision outcome**, not necessarily CPU reduction. Measure baseline completeness and actual intervention first. If the incumbent already produces a correct actionable dossier, the new wrapper may offer no incremental benefit. Do not assign a wage saving to shorter report-reading without observed duration. Human break-even thresholds can show what labor duration would be needed to cover a completely specified automated cost, but unknown inference, integration and maintenance costs prevent an observed fully loaded monetary claim.

A retained recipe supplied by the research assistant is researcher-authored integration. It is not autonomous discovery. If it ties a straightforward conventional script, state that plainly. The enterprise can adopt the better conventional implementation; that admission would be an engineering decision. Payback additionally requires supported recurring use, incremental value and complete investment costs. No such positive result is implied by this screen.
