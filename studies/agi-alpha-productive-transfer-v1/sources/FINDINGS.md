# Production baseline audit

## Result

The existing component-decision lane is already deterministic. A transferred method should address a new, evidenced bottleneck rather than redescribe existing deterministic verification as DUPLEX.

The exact original component protocol assesses one consumer revision plus one changed dependency tuple. Its six historical transitions produce 18 arm observations, not 18 independent customer jobs. All builders may reuse eligible sources, wheels, environments, and exact-bound baseline evidence. The current builders choose fresh before/after execution in parallel. The actual incumbent is a researcher-assisted workflow constructed in the prior study, not an observed no-AI human service.

## Measured burden

Read-only aggregation of the 18 unique target-observation files gives median observer wall 15.231291493 seconds and CPU 0.216800308 seconds. The mandatory actual-timeout case alone has median wall 15.015802733 seconds. No runtime model calls occur. Exact source and row identities are in `baseline-audit.json`.

The timeout is the actual 15.0-second consumer constant; the verifier rejects apparent timeout evidence below 14.999 seconds. Substituting a clock or reducing this threshold would redefine the accepted work. A baseline cache would reduce one side's CPU and instrumentation but cannot remove the fresh target's timeout from elapsed completion, since both sides already run in parallel. All arms already have baseline-cache permission.

## Useful output and limits

An accepted outcome is a complete, source-bound scoped component preservation or substantiated regression decision, including an exact lock diff, raw observations, evidence identities, bilingual action and remaining requirements. Unknown complete cost and attention stay unknown; actual customer receipts remain zero. A component pass advances evidence for full application qualification and does not permit adoption of the native application lock. The 61 assertions do not prove all input behavior, platform support, authentication, persistence or release readiness.

## Concrete new transfer seam

The current product's `contrib/upgrade_decision/core.py` accepts a curator-authored `alpha-upgrade-call-request/v1`: raw public source identities plus 1–24 exact selected consumer calls, source locations and before/after target declarations. It already implements source validation, custom constraint binding, an independent `inspect.Signature.bind` comparator, creator/critic/verifier and portable delivery.

The missing intake operation is selection and attribution of consumer-relevant calls from source and an upgrade brief. A substantive DUPLEX adaptation could use an actual model to propose this structured evidence while deterministic tools validate source spans, import/receiver relationships, call shapes and before/after constraints. It should compare against the present curator-assisted workflow and a strong ordinary AST/import/dataflow extractor allowed the same retained source assets. Model proposals and corrections must be retained; model-only conclusions or unsupported runtime relationships must not be accepted. An ablation can remove exact verification and quantify false allegations without deploying it.

Static argument binding is narrower than behavioral compatibility. Its acceptance contract must remain explicit. Direct Python imports can be checked under standard-import/no-monkeypatch assumptions. Dynamic `*args`/`**kwargs`, decorated targets, ambiguous receiver dispatch and runtime mutation require abstention or separately authorized execution. A model's plausible mapping is not a proof.

No fresh evaluation target or expected outcome has been executed by this audit. The independent confirmation oracle should be constructed and sealed separately from candidate development. A task-family separation from the previous Starlette/Pydantic consumer study is required; mere new representations or arm reruns are not new demand.
