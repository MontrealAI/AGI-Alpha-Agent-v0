## Metrics and provenance qualifications

1. The confirmation commitment hashes workflows, runner, protocol, benchmark manifest and evaluator. It does
   **not** include a digest of the exact per-arm spawn messages. Archive those actual messages as transcript-
   derived provenance and distinguish any after-run archival record from a precommitted byte identity.
2. The runner records successful interface operations. Failed parser, invalid-path or read invocations can fail
   before appending an event or advancing persistent counters. The development concurrent-read failure is
   disclosed and the original runner is retained; a file lock fixes the demonstrated serialization issue before
   confirmation. Describe counts as **logged successful operations**, not complete tool-call or cost telemetry.
3. Wall time combines hosted reasoning, scheduling and orchestration. It is not matched hidden computation,
   provider usage or CPU time. With one run per arm, a latency contrast is descriptive and confounded by case
   order/server conditions. It cannot establish monetary Alpha.
4. File confinement is protocol-level. `python -c` can execute arbitrary file operations from a submitted command;
   the runner does not provide OS security. The paper does not claim otherwise. Logs can document compliant
   commands, but cannot prove a malicious participant had no other access.
5. The E method predates development. The further helper is researcher-directed construction during a synthetic
   development delivery. It is not a paid customer discovery, a model weight update or an autonomous scientific
   breakthrough. Its deep-copied observation baseline is a useful concrete design choice; fresh benefit remains
   the E+ versus E comparison, not byte transfer or code novelty.
