EFFICIENCY AND EXACTNESS

A local probe emitting 1,048,576 binary bytes as base64 was truncated at about
1 MiB of text despite a larger token budget; its JSON was invalid. Do not use
that read size. A 524,286-byte probe arrived intact with exactly 699,048 base64
characters. This is a measured local bridge bound, not a discovered connector
upload ceiling. The connector schema declares no request-size limit. The earlier
4.3 MB blob failure makes large untested requests an unnecessary risk.

In functions.exec, call read_review_payload.py through exec_command with
max_output_tokens=250000; parse the returned JSON directly into a JS variable.
Validate exit code, byte count and base64 length. Do not text()/notify() the
content. Pass it to create_blob. Compare the returned SHA to git_blob_sha1 from
the local helper. After constructing the additive tree and an unreferenced
commit, use fetch_file with encoding='base64', ref=<that exact commit SHA>, and
the exact repository path. Normalize only base64 line wrapping, then compare
the entire returned base64 content with the original local payload. This exact
readback route was verified with a 522,050-byte existing module. The connector's
fetch_blob and generic /git/blobs GET normalize content to UTF-8; do not use them
for binary-byte verification. Complete readback before creating the branch or
PR. This verifies actual remote file bytes without printing binaries or passing
megabyte command strings through a shell.

Read larger standalone PDFs in multiple bounded slices if needed. Use chunk
lengths divisible by three so their base64 strings concatenate correctly; only
the final slice may contain '=' padding. Compare the final remote blob SHA with
the complete local file's independently calculated Git blob identity. An explicit
manifest should hold full-file identities before any upload begins.

Use ordinary shell quoting for helper paths, not JSON.stringify as shell escaping.
The upload loop should log only ordinal, remote path, bytes, expected/returned
hash and readback status. Keep a local receipt of created object SHAs so an
interruption resumes without rewriting data or creating duplicate commits.

Perform content mutations sequentially. GitHub documents general secondary
limits of 80 content-generating requests per minute and 500 per hour, with lower
endpoint-specific limits possible. A roughly one-second spacing plus normal
response latency stays below the general per-minute ceiling for this small
campaign, but observe any actual Retry-After/rate-limit response. Stop on an
error, record it, and respect the returned wait; do not blind-retry or switch
accounts to evade limits. All source/text batches plus approximately 115–130
