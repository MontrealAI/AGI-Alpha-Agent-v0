# Automated committed-source assurance

This additive offering turns an approved public-source manifest into a finished
source-assurance package. It automatically extracts declared and observed source
identities, compares them with the existing catalogue specialist, checks the
complete result, exports the actionable CSVs and recoverable workspace, and writes
a finished report. An empty action plan is useful when no drift is found; it does
not approve the behavior or security of the inspected code.

This is foreground local Node execution. It creates no account, credentials,
approved operator home, background scheduler, financial operation or general
repository-code executor. Its technical acceptance is distinct from customer
acceptance and from authenticated browser-to-approved-executor qualification.

## What changed from the earlier contribution

The earlier source-mission runner had two hard-coded inputs, overwrote its output
files and depended on manually assembled reporting and inspection. The new runner
has an explicit bounded plan and approval digest, automatic input preparation and
report packaging, immutable checkpoints, source-bound reconnect, duplicate handling
and STOP. It calls the same existing `examples/ti-guide/guide.mjs` specialist;
novelty does not replace a better existing comparison method.

After the caller approves the manifest, exact Git commit, output identity and
finite allowance, the supported mechanical job needs no routine operator handling.
That statement describes the observed local calls, not a measured zero exception
rate across production. Choosing the permitted source scope, approving it and
deciding whether proposed corrections should be commissioned remain user decisions.
Engineering, installation, maintenance, customer acceptance and genuine exceptions
are separate cost categories. They are not erased or charged as fresh bespoke
engineering on every delivery.

The machine-readable [workflow map](workflow-automation-map.json) classifies all
eight stages and the remaining activities. The product's separate shared economic
model supplies prices, utilization, reserves and amortization; this runner does not
invent a complete cost from its process timings.

## Current successor and preserved predecessor evidence

The additive [completion candidate](../completion-v3/README.md) now creates
`alpha-source-assurance-plan/v3` approvals with an explicit expiry, attempt ceiling
and aggregate execution allowance. Durable reservations charge the full allowance
before source validation or work, including interrupted attempts and completed
rechecks. Cancellation is distinct from a resumable STOP. This is still local
foreground execution; it does not establish a persistent browser connection or
an approved installed profile. The earlier v2 plans and evidence below retain
their original identities and scope.

Source reads now use Git's explicit `--no-lazy-fetch`, `--no-replace-objects` and

installed combinations remain unqualified. The earlier

## Cost interpretation

Stage receipts contain measured whole-number microseconds, local Node CPU, fixed
Git read counts and zero service model calls. Stage CPU explicitly excludes child
Git CPU. Planning facts, invocation/recovery overhead and final full revalidation
are recorded separately; summing narrow stage times is not complete process cost.

The external wrapper uses a monotonic clock and POSIX `wait4` to observe launch,
imports, the Node command and its waited descendants. Linux maximum RSS is an
observation for the command, not a sum of simultaneous fleet memory. Complete
monetary cost, operational exception rate, hardware prices, allocated development
and maintenance, and traditional human task duration remain unknown here. The
zero model-call observation applies only to the deterministic service; it does not
erase the model-assisted engineering that created or reviewed it.

No observed human-work saving, collected revenue, reinvestable surplus, capability
superiority or self-acceleration follows from these measurements. There are no
token or payment interfaces in this offering.

## Run a new approved scope

Use a fresh run ID; prior plans and delivered files are never overwritten.

```sh
node contrib/productive-capability-ledger/automation-v1/run-mission.mjs plan \
  --manifest docs/try/sources.json \
  --ref 0255ebf0a3289e1011f3a8fad165baf140480241 --run-id NEW-RUN
```

Inspect the returned plan and exact approval digest. Then pass its returned
`planFile` and `approvalDigest` to:

```sh
node contrib/productive-capability-ledger/automation-v1/run-mission.mjs run \
  --plan RETURNED-PLAN-PATH --approve RETURNED-DIGEST
```

The corrected CLI confines output to `corrected-plans/` and `corrected-runs/`.
Inputs admit only committed ordinary Git files with modes `100644` or `100755`,
1–128 explicit source paths and the existing catalogue limits. Untrusted task data
cannot add operations or authority. A `STOP` file in that run directory stops the
next stage and preserves its checkpoints; explicit removal permits the same
approved scope to resume. An already completed request returns checked historical
work plus new reconnect observations rather than executing a new mission.

The exported `makePlan`/`runPlan` API allows a host-selected test output root; that
host configuration is not an imported task field. It must remain inside the
calling application's existing write authority.

```sh
node --test contrib/productive-capability-ledger/automation-v1/run-mission.test.mjs
python contrib/productive-capability-ledger/automation-v1/verify-run.py \
  contrib/productive-capability-ledger/automation-v1/corrected-runs/corrected-auto-guide-0255
```

Authenticated browser-to-approved-executor testing, public deployment and fresh
installation remain separate receiving-owner qualification. Their absence does
not prevent the separate, honestly labeled automated-cost scenario analysis.

New v3 plans default to 20 seconds per invocation, eight invocations, 160 reserved
seconds total and expiry one hour after creation. The CLI accepts `--max-seconds`,
`--max-attempts`, `--total-seconds` and exact-ISO `--expires-at`; all enter the
approval digest. An invocation reserves its full per-invocation allowance without
refund, even if it crashes or only revalidates completed output. These are
conservative authorization reservations, not measured CPU time or a monetary bill.
Exhaustion requires a new plan, new run identity and explicit new approval.
The host may create `CANCEL` to cancel; the runner records `CANCELLED.json` and
refuses subsequent execution even after the signal file is removed. Neither
control file is a remote authorization interface. An interrupted `recovery.lock`
requires operator inspection; it is never silently reaped.
