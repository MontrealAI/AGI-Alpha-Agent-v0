# Protected Flywheel operating slice / Parcours opérationnel protégé

## English

This implementation extends the existing signed Journal, TransformationLibrary, native operator and API.
The public [Flywheel](../flywheel/index.html) remains a free simulation and preparation experience.
Opening it performs no provider call, wallet signature, transaction, customer contact or protected-service request.

The first supported retained implementation is the existing closed source-evidence selector:
a typed public document, a bounded selection program and an immutable acceptance charter produce an
attributable source-clause summary. Imported Python, shell, instructions, dependencies and dynamic imports
are not supported capsule contents. This finite public algorithm family does **not** itself establish Alpha
over competent current models and ordinary tools. A correctly rejected candidate is an expected outcome.

### Current operating map

| Stage | Implemented boundary | Qualification still required |
| --- | --- | --- |
| Explore | Existing public deterministic commercial simulation | No actual sales or model-quality inference |
| Prepare | Existing Alpha project, history, exports, recovery and handoffs | Exact beneficiary, rights, acceptance, resources and actions |
| Execute | Opt-in native provider connector; one signed, bounded attempt; no implicit retry | Approved endpoint, exact served model ID, requested versus served reasoning, tools, quota, billing and budget |
| Learn | Accepted originating Journal record, complete A costs, frozen encrypted candidate, prospective matched plan, separate evidence, assessment, validation and admission | Actual frontier paired runs, independently informative acceptance and complete B costs |
| Reuse | Resource-specific wallet proof; fresh two-reader ENSv1 checks; closed local execution; durable attempt, failures and unknown cost | A different eligible name **and wallet**, fresh accepted work, reconciled all-resource costs and current matched Beta |
| Requalify | Changed Beta/policy removes active pointers; finite expiry; recursive dependency checks; terminal revocation | Fresh affected evidence; supersession is not automatic economic improvement |

No deployment-specific live ENS qualification, actual frontier trial, paid customer receipt, production
capsule deployment or measured real peer advantage is established by the conformance fixtures.
The native status endpoint reports this limit. Synthetic test wallets, code pins, receipts, prices,
budgets and acceptance statements are fictional; their cryptographic checks execute real software.

### Native operation and service boundary

The existing operator adds:

~~~sh
alpha-agent --home /private/agent serve --flywheel-deployment /operator/protected-deployment.json
alpha-agent --home /private/agent flywheel --deployment /operator/protected-deployment.json --output /private/status.json status
~~~

The server still binds to numeric loopback. Existing operator endpoints retain their bearer-token protection,
request limits and security headers. Exposing a service through an approved HTTPS proxy, including host,
transport, request-rate, storage and monitoring configuration, is a separate provisioning step.
The public website never receives an operator token, model credential or encryption key.

A deployment file must contain exactly schema_name=protected-flywheel-deployment/v1, service, producer,
trust_path, checkpoint_path, readers, ens_pins, keys and active_key. The keys mapping identifies private
32-byte AES-256 key files; it does not contain key bytes. Two separately approved Ethereum-mainnet RPC
providers with different hostnames and independently checked Registry, Wrapper and Registrar SHA-256
implementation pins are mandatory. Existing read-only RPC transport is reused; it cannot broadcast.
No default endpoint, model, code pin, credential or trusted signer is invented.

Commands candidate, plan, evidence, validate, admit, revoke, rotate-key, reuse-acceptance and account consume
separately signed, journal-bound decisions. model-run additionally requires a controller-signed model permit
with the exact request/configuration, requested reasoning, no-external-tools manifest, quota evidence,
finite expiry and charge allowance. This first connector uses the existing JSON-completion transport.
Responses/tool/computer-use executors require their separately approved connector and qualification.
An available subscription does not establish an API entitlement. Missing access refuses before a call.

The protected API exposes /api/flywheel/status, /challenge, an authenticated /catalog and per-capsule /manifest and /invoke beneath
/api/flywheel. Without provisioned resources it returns 503 for protected work. There is no plaintext
capsule-download endpoint. Manifest discovery and invocation each require their own one-time, two-minute,
service/purpose/resource/request-bound EIP-191 challenge. Challenge issuance is bounded globally and per
wallet. No session cookie or browser-supplied name grants eligibility.

Supported authority is deliberately narrow: an exact lowercase ASCII direct label under agent.agi.eth,
EOA wallet control, current ENSv1 Registry authority or NameWrapper ownership, live parent/wrapped expiry
and unexpired agi.eth registration. Code pins, current block age, canonical block hash, reader agreement
and ownership are checked at every resource crossing. Delegations, contract-wallet signatures,
internationalized labels, CCIP/offchain names and ENSv2 are unsupported; their qualification cannot be
inferred from a fixture. Approved providers and namespace protocol selection remain trust dependencies.
No existing Jobs club.agi.eth validator role, contract, currency route or settlement rule changes.

### Evidence, economics and admission

A records all resources for accepted delivery, including learning during that job. B records only extra
extraction, generalization, testing, retention, distribution, revalidation and reuse. C records separately
authorized extra investment. An activity ID cannot be charged into two buckets. Every paired evaluation
invocation must have its exact signed receipt charged once in the frozen B record. Zero-cost categories
require an explicit signer attestation; unknown amounts remain unknown. All nine resource categories must
be reconciled before a delivery, retention or reuse cost record can be sealed.

Offers, invoices and pending payment create no collected revenue. Capital is separate from revenue.
Amounts are integer USD micro-units, separate from AGIALPHA utility or token transfers.
Reports distinguish complete-cost profit, cash, obligations, reserve and available funds. Unknown costs
prevent complete-cost profit or available-funds claims. Collection records are attributed accounting
attestations with evidence commitments; no bank verification or real collection is claimed here.

Only an exact accepted originating mission with complete A costs can produce a candidate. The original
agent's wallet must already have the existing wallet-control binding and fresh eligible ENS authority.
A frozen plan names current Beta/policy, the same frontier model/reasoning/tools/resource rules, the
recipient's existing capability commitment, excluded delivery inputs, fresh inputs, a prospective reuse
count, uncertainty basis and the complete B cost record. Executions must follow freeze. Configured
execution custodians attest response/output/usage/billing identities; acceptance uses distinct configured
keys and separately informative tests. Signatures bind attestations; they do not establish their truth
or organizational independence.

Correctness and economic value are separate. The supported lower net saving per use cannot exceed the
least observed paired saving. Its prospective reuse value must exceed already incurred B plus declared
remaining retention costs. A is never charged again. This conservative finite rule is not a calibrated
general demand forecast, statistical confidence procedure or automatic proof of transferable value.
Insufficient or negative evidence rejects; failures remain in audit history, outside active admissions.

Validation and admission require separate configured roles and current bindings. Local structural-library
promotion does not touch protected admissions. Imported state cannot install signers, keys or executors.
An invocation produces an executed receipt, not a successful-reuse claim. The latter requires independent
acceptance, a fresh current Beta receipt and all-resource cost reconciliation. Attributable additional
value may be negative; accepting useful work does not imply a positive economic advantage.

### Storage, keys, recovery and revocation

The protected branch lives inside the existing TransformationLibrary journal record. Public manifests
remain separate from AES-GCM encrypted closed-program bytes. AAD binds service, journal and exact versioned
manifest. Historical signed Journal snapshots preserve ciphertext and audit history. Existing private
backups preserve that history; they contain the runtime identity key and remain private.
Encryption keys are separately provisioned and excluded from those backups, bundles, logs and public pages.

The service owner must designate key custody, encrypted independent backup, rotation and recovery.
Rotation reencrypts current records under a separately provisioned active key. Historical backups still
require historical keys; removing an old key does not rewrite immutable history. Loss of necessary keys
fails closed. No credentials or production keys are created by loading a capsule or deployment file.

A separately provisioned DurableCheckpoint must live outside portable runtime recovery state, preferably
on independently retained durable custody. Every protected state mutation and successful resource crossing
advances its monotonic high-water record before local commit. A crash between those commits may require
explicit recovery; it refuses rather than accepting an older journal. Restoring an old backup cannot
silently resurrect a revocation while current checkpoint custody is retained. A file on the same host is
not independent remote durability, and rolling back both stores defeats that protection.

Access is reconsidered at discovery and invocation, including dependencies and revoked configured
signers. Changed models/policies require fresh evidence; terminal revocation cannot be promoted again.
A new version is necessary for a revoked method. Controlled execution limits direct export; observable
outputs may reveal behavior, especially for this small public selector family. Disclosed plaintext and
learned behavior cannot be clawed back. There is no permanent-scarcity or accumulating-moat claim.

### Approval needed for qualified live completion

The independent implementation can be reviewed and tested without provisioning production authority.
Actual qualification requires the operator's approved service origin/host and durable storage; independently
provisioned keys, trusted role registry and checkpoint custody; two approved RPC readers and real code pins;
approved frontier executor/model configuration with a specific finite spend allowance and quota/billing
evidence; and two eligible owner-controlled agent wallets signing fresh challenges.
No private key or seed phrase should be provided to this application or in a repository.

## Français

Cette implémentation prolonge le Journal signé, la TransformationLibrary, l’opérateur et l’API existants.
Le [Flywheel public](../flywheel/index.html) reste une simulation gratuite et un parcours de préparation.
Son ouverture ne déclenche ni modèle, signature, transaction, contact client ou requête au service protégé.

La première implémentation conservée utilise le sélecteur fermé de preuves documentaires existant :
document public typé, programme borné et charte d’acceptation immuable produisent un résumé traçable.
Les capsules n’acceptent ni Python, shell, instructions arbitraires, dépendances ni imports dynamiques.
Cette petite famille publique d’algorithmes ne démontre pas, à elle seule, un Alpha face aux modèles
frontière et outils ordinaires compétents. Un rejet justifié constitue un résultat attendu.

| Étape | Frontière implémentée | Qualification restante |
| --- | --- | --- |
| Explorer | Simulation commerciale déterministe publique existante | Aucune vente ni qualité réelle de modèle déduite |
| Préparer | Projet Alpha, historique, exports, reprise et transmissions existants | Bénéficiaire, droits, critères, ressources et actions exacts |
| Exécuter | Connecteur natif facultatif ; tentative unique signée, bornée, sans reprise implicite | Accès approuvé, modèle réellement servi, raisonnement demandé/servi, outils, quota, facturation et budget |
| Apprendre | Mission d’origine acceptée, coûts A complets, candidate chiffrée figée, plan prospectif apparié, preuves, évaluation, validation et admission distinctes | Exécutions frontière réelles, acceptation informative indépendante et coûts B complets |
| Réutiliser | Preuve de portefeuille propre à la ressource, ENSv1 frais auprès de deux fournisseurs, exécution fermée et historique durable | Nom ET portefeuille différents, tâche nouvelle acceptée, coûts complets et Beta actuel apparié |
| Requalifier | Retrait des pointeurs actifs après changement Beta/politique, expiration, dépendances récursives et révocation terminale | Nouvelles preuves affectées ; aucune amélioration économique automatique |

Les tests de conformité ne qualifient ni ENS réel, ni modèle frontière réel, ni encaissement client,
ni déploiement de production, ni avantage réel d’un autre agent. Portefeuilles, contrats, reçus, prix,
budgets et acceptations des tests sont fictifs ; les vérifications cryptographiques exécutent du vrai logiciel.

L’opérateur existant accepte serve --flywheel-deployment et flywheel avec --deployment et --output.
Le serveur reste lié à l’interface locale numérique. Les protections existantes des routes opérateur,
tailles de requêtes et en-têtes demeurent. Un proxy HTTPS, ses hôtes, limites, stockage et surveillance
exigent un provisionnement approuvé distinct. Aucun jeton opérateur, secret modèle ou clé de chiffrement
n’entre dans le site public.

Le fichier de déploiement contient exactement schema_name=protected-flywheel-deployment/v1, service,
producer, trust_path, checkpoint_path, readers, ens_pins, keys et active_key. keys référence des fichiers
privés de 32 octets, sans contenir leurs clés. Deux fournisseurs RPC Ethereum principal approuvés,
aux hôtes distincts, et les empreintes SHA-256 vérifiées du Registry, Wrapper et Registrar sont obligatoires.
Le transport RPC existant reste en lecture seule. Aucun fournisseur, modèle, tarif, secret, signataire
ou empreinte fictive n’est choisi par défaut.

Les décisions candidate, plan, evidence, validate, admit, revoke, rotate-key, reuse-acceptance et account
exigent des signatures distinctes liées au Journal. model-run exige en plus un permis du contrôleur :
requête/configuration exactes, raisonnement demandé, manifeste sans outils externes, preuve de quota,
expiration et allocation bornée. Ce premier connecteur utilise le transport JSON-completion existant.
Les exécuteurs Responses, outils et ordinateur demandent leur connecteur approuvé et leur qualification.
Un abonnement ne prouve aucun droit API. L’absence d’accès bloque avant l’appel ; une réponse perdue
reste une tentative incertaine facturable et ne déclenche aucune reprise automatique.

L’API ajoute /api/flywheel/status, /challenge et un /catalog authentifié, ainsi que /manifest et /invoke propres à chaque capsule.
Sans ressources provisionnées, le travail protégé retourne 503. Aucune route ne télécharge la capsule
en clair. Découverte et invocation exigent chacune un défi EIP-191 unique de deux minutes, lié au service,
à la finalité, à la ressource et à la requête. L’émission est bornée globalement et par portefeuille.
Un nom saisi ou une session de navigateur ne crée aucune admissibilité.

La politique couvre seulement un libellé ASCII minuscule directement sous agent.agi.eth, un portefeuille
EOA, l’autorité ENSv1 actuelle du Registry ou du NameWrapper, les expirations des parents enveloppés
et l’enregistrement agi.eth non expiré. Empreintes de code, âge du bloc, hachage canonique, accord des deux
lecteurs et propriété sont revérifiés à chaque accès. Délégations, portefeuilles contrats, noms
internationalisés, CCIP/hors chaîne et ENSv2 ne sont pas pris en charge. Les fournisseurs approuvés
et le choix du protocole de l’espace de noms restent des dépendances de confiance.
Les rôles Jobs club.agi.eth, contrats, devises et règlements restent inchangés.

A couvre la livraison acceptée, apprentissage pendant ce travail compris. B ne couvre que les coûts
supplémentaires d’extraction, généralisation, tests, conservation, distribution, revalidation et réutilisation.
C couvre l’investissement supplémentaire séparément autorisé. Un identifiant d’activité ne peut être
facturé dans deux catégories. Chaque invocation d’évaluation appariée doit être liée à son reçu exact
et facturée une seule fois dans B. Une catégorie à zéro nécessite une attestation explicite ; un montant
inconnu reste inconnu. Les neuf catégories de ressources doivent être rapprochées avant clôture des coûts.

Offre, facture et paiement en attente ne créent aucun revenu encaissé. Le capital reste distinct.
Les montants sont des micro-unités USD entières, séparées d’AGIALPHA et des mouvements de jetons.
Les rapports distinguent profit à coûts complets, trésorerie, obligations, réserve et fonds disponibles.
Un coût inconnu bloque les affirmations de profit complet et de fonds disponibles. Les encaissements
sont des attestations comptables attribuées, liées à des engagements de preuve ; aucune vérification
bancaire ou recette réelle n’est établie ici.

Une candidate exige une mission d’origine acceptée et ses coûts A complets. Le portefeuille de l’agent
d’origine doit être déjà prouvé par la liaison existante et disposer d’une autorité ENS admissible actuelle.
Le plan figé nomme Beta/politique courants, modèle frontière, raisonnement, outils et règles de ressources
identiques, capacités du destinataire, entrées d’origine exclues, entrées nouvelles, horizon prospectif,
incertitude et registre B complet. Les exécutions suivent le gel. Des dépositaires configurés attestent
réponses, résultats, usage et facturation. L’acceptation utilise des clés distinctes et des tests
indépendamment informatifs. Une signature lie une attestation sans établir sa vérité ou son indépendance organisationnelle.

La correction et la valeur économique restent distinctes. La borne prudente d’économie nette par usage
ne peut dépasser la moindre économie appariée observée. Sa valeur prospective doit excéder B déjà engagé
et les coûts futurs déclarés ; A n’est jamais refacturé. Cette règle finie ne constitue ni prévision
générale de demande, ni procédure statistique calibrée, ni preuve automatique de transférabilité.
Une preuve négative ou insuffisante produit un rejet conservé dans l’audit, hors admissions actives.

Validation et admission exigent des rôles distincts et des liaisons courantes. La promotion locale
structurelle ne touche pas aux admissions protégées. Un import n’installe ni signataire, clé ou exécuteur.
Une invocation crée un reçu d’exécution, sans revendiquer une réutilisation réussie. Celle-ci demande
acceptation indépendante, reçu Beta actuel sur la tâche nouvelle et rapprochement de tous les coûts.
La valeur supplémentaire peut être négative : une tâche utile acceptée ne prouve pas un avantage économique.

La branche protégée reste dans le Journal de la TransformationLibrary. Les manifestes publics sont
distincts des programmes chiffrés AES-GCM ; les données associées lient service, Journal et manifeste
versionné. L’historique signé et les sauvegardes privées existantes conservent chiffrement et audit.
Ces sauvegardes contiennent la clé d’identité du runtime et doivent rester privées. Les clés de chiffrement
sont provisionnées séparément et exclues des sauvegardes, bundles, journaux et pages publics.

Le propriétaire doit définir garde, sauvegarde chiffrée indépendante, rotation et récupération des clés.
La rotation rechiffre les objets courants sous une clé active séparément provisionnée. Les sauvegardes
historiques nécessitent encore les anciennes clés ; l’historique immuable n’est pas réécrit. Une clé perdue
bloque l’accès. Charger une capsule ou configuration ne crée aucun secret ou droit de production.

Un DurableCheckpoint séparément provisionné reste hors de la reprise portable, idéalement sur une garde
durable indépendante. Chaque mutation protégée et accès réussi avancent ce seuil monotone avant la
validation locale. Une panne entre les deux validations peut nécessiter une récupération explicite :
elle bloque plutôt que d’accepter un Journal antérieur. Une ancienne sauvegarde ne peut restaurer
silencieusement une révocation tant que la garde actuelle est conservée. Un fichier sur le même hôte
n’est pas une durabilité distante indépendante ; restaurer les deux registres annule cette protection.

Découverte et invocation recontrôlent accès, dépendances et signataires révoqués. Un changement de modèle
ou politique exige de nouvelles preuves. Une révocation terminale impose une nouvelle version.
L’exécution contrôlée limite l’export direct ; les sorties peuvent révéler un comportement, surtout
pour cette petite famille publique. Le texte divulgué et les comportements appris ne sont pas récupérables.
Aucune rareté permanente ni croissance automatique d’un avantage défendable n’est revendiquée.

La qualification réelle exige : origine/hôte de service et stockage durable approuvés ; clés, registre de rôles
et garde du seuil provisionnés indépendamment ; deux lecteurs RPC et vraies empreintes ; exécuteur/modèles
approuvés avec allocation financière finie et preuves de quota/facturation ; deux portefeuilles d’agents
admissibles contrôlés par leurs propriétaires pour signer des défis nouveaux.
Aucune clé privée ou phrase de récupération ne doit être fournie dans l’application ou le dépôt.
