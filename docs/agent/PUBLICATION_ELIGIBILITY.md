# Explicit release publication eligibility

Ordinary main pushes and reusable release-acceptance calls run qualification only. They retain the complete package/build/install/archive qualification and its CI artifact, but cannot reach Pages or release-publication jobs. The native manual-dispatch inputs `publish_version` and `publish_draft_id` default to empty strings. An empty version requests qualification only. Publication requires a separately approved exact source/version campaign, the exact committed version, and the ID of its previously approved, already staged draft release.

## Approved operator sequence

1. Review current main, the declared version, release scope and completed qualification. Obtain the owner's approval for the specific release campaign and its staging/publication actions. Successful CI alone does not authorize them.
2. In that separately approved campaign, stage the intended new version's tag at the exact reviewed current-main commit and its draft release with `target_commitish` set to that full commit SHA. Record the resulting release ID. Staging is a separate write operation: this guard never creates a draft or tag, grants permissions, moves a tag or uploads assets. Do not run the existing monolithic publisher merely to stage a draft; it also uploads and publishes. No permanent test release or unrelated fixture is needed.
3. Select `Agent release acceptance` on main through GitHub's workflow-dispatch interface. For qualification only, leave both inputs empty. For separately approved publication, enter exactly the committed version and the known draft's positive decimal ID. For example, `1.34.0` is appropriate only after its final source/version and campaign have been approved. Inputs do not change source, version or permissions.
4. The early read-only gate checks the repository/ref, actual checkout HEAD, raw committed version bytes and platform dispatch event. It resolves the existing exact-version tag to current tested main, reads the exact known release ID with this job's token, and requires that response to be a nonpublic, non-prerelease draft for the same tag and full source SHA. A bounded listing must contain that same ID/tag exactly once with matching identity. A public or conflicting by-tag result refuses. All identity observations and intent/source checks repeat to detect drift.
5. Every original acceptance dependency remains mandatory. Explicit publication runs repeat the check before packaging; qualification-only packaging remains unchanged. Pages and publisher jobs require the early result. Fresh checks run before Pages configuration, immediately before Pages deployment and before publisher entry. The original `release_context` command remains immediately before deployment alongside the new gate. Artifact manifests must match source/version. Existing final publisher checks remain unchanged.
6. Review terminal workflow and public readback evidence. A refusal, absent draft, unknown visibility or unknown outcome is not permission to guess another ID, change token scope, move a tag or overwrite public assets.

## Effective draft visibility and hosted qualification

The repository's `permissions.push` boolean does not establish a narrowed GitHub App installation token's effective draft visibility and is not used as proof. An empty listing or by-tag 404 does not prove draft absence. Eligibility instead requires an actual successful read of the specified intended draft ID, matching source/tag identity, and matching listing under the same token. Missing, inaccessible, public, incorrectly targeted or conflicting drafts fail closed. A source label or mocked response is not hosted evidence.

The minimal hosted qualification is a separately approved read-only invocation using the exact workflow job's existing token, context and candidate source against the already staged intended release draft. Retain only the sanitized result: repository/source/version, draft ID, tag commit and observed draft identity. Do not print tokens, headers, full event payloads or release bodies. The early gate can establish this observation before any Pages/publisher job, but a publication dispatch also requests the later write path; a read-only rehearsal must use an explicitly reviewed no-publication harness instead. No such hosted rehearsal or intended draft is claimed to exist yet. If the current token cannot read it, stop and review the design; never expand permissions automatically.

## Bounds and trust

The guard makes only GET requests to the fixed GitHub API origin with the workflow's existing token, default TLS verification, no redirects/retries, at most 32 requests in 120 seconds, 20 seconds per request, 2 MiB per response and 16 MiB total. Listing is capped at 100 releases in ten 10-entry pages. Only exact tag/by-tag lookups may map 404 to absence, and neither absence can authorize publication. A known-ID 404 always refuses. A draft must reference an already existing exact-source tag; absent tags refuse. Existing public versions refuse re-publication, including same-source versions, preserving their Pages/tag/assets identity.

`GITHUB_EVENT_PATH` and platform context are authoritative only within trusted GitHub workflow execution. Copying an event or setting environment variables elsewhere does not authenticate owner approval. The guard assumes reviewed source and trusted platform execution; it is not an authorization service or a hostile-local-filesystem proof. Rechecks do not make independent GitHub operations atomic. All downstream gates and owner approvals remain necessary.

This correction does not change version `1.33.0`, historical releases/tags/assets or deployment records. A future `1.34.0` campaign needs its own final version, notes, documentation inventory, exact-source tests and staging/publication approval. Release publication authorizes no blockchain or hardware operation.

Primary platform references: [workflow-dispatch syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onworkflow_dispatchinputs), [event payload](https://docs.github.com/en/webhooks/webhook-events-and-payloads#workflow_dispatch), [release listing](https://docs.github.com/en/rest/releases/releases#list-releases) and [exact release-ID lookup](https://docs.github.com/en/rest/releases/releases#get-a-release). The event ref accepts `main` or `refs/heads/main`; the independently checked platform ref must be exactly `refs/heads/main`.
