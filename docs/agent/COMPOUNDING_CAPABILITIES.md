# Compounding useful capabilities: operating guide and evidence

**AGI ALPHA now has a source-executed example of a bounded enterprise whose accepted software assets support later work and a distinct successor.** Its benefit is concrete: it preserves executable programs, checks their continued applicability, and avoids repeating valid construction. The experiment also exposes where that approach loses: a supplied expert implementation is cheaper, and inherited validation can cost more than direct validation.

This guide separates three layers. **Layer 1 is executed software and retained evidence. Layer 2 is an economic hypothesis requiring a voluntary payer and measured costs. Layer 3 is a proposed progression into physical instruments and productive infrastructure.** Success in one layer does not establish the next. AGI ALPHA is the project identity; this work establishes neither achieved AGI nor guaranteed commercial success.

## Layer 1 — the bounded enterprise that actually ran

### Run and inspect it

After the repository's documented setup, use Node **22.17.1** from the repository root:

```sh
node examples/successor-workbench/compounding-probe.mjs > NEW_FILE
```

Replace `NEW_FILE` with a new output path: shell redirection can overwrite an existing file. No wallet, network service, payment provider or added credential is needed. This command runs the existing mathematical enterprise components, then the existing controller; it adds no alternative controller. The output contains source identities, every counted charge, hashed receipts, nine workload comparisons, changed-condition results and the completed workspace.

Inspect `components.state`, `components.scenarios`, `components.changed`, `components.ledger` and `enterpriseJourney`. The expected successful states are `PASSED_COMPONENT_CRITERIA` and `SUCCESSOR_ACCEPTED_LOCAL`. A failure remains a failure with its retained partial evidence. Inspect the underlying receipts before drawing conclusions from either label.

This is a **dated, source-bound reproducer**, not an ordinary CI gate or a requirement to keep the repository immutable. It checks the accepted source manifest used by the experiment. A source mismatch means this frozen reproduction no longer describes the installed bytes; reproduce its matching revision or bind a subsequent evaluation to the changed source. Do not substitute the old result for a new release's evidence. The optional standalone check is:

```sh
node --test examples/successor-workbench/compounding-probe.test.mjs
```

That test executes the campaign again and incurs additional work. Test repetitions must be recorded separately from the two decisive evaluations described below.

### What survives one mission and enables another

The existing [foundry](../../examples/autonomous-enterprises/foundry.mjs) searches a supplied finite grammar, and a separate [checker](../../examples/autonomous-enterprises/checker.mjs) qualifies the resulting exact-rational programs. Six initial assets are retained with their executable representation, digest, dependencies and certificates:

| Asset | Dependency | Productive use |
| --- | --- | --- |
| Identity, dimension 1 | None | Construction base |
| Walsh transform, dimension 2 | Identity | Exact transform |
| Walsh transform, dimension 4 | Walsh-2 | Exact transform |
| Walsh transform, dimension 8 | Walsh-4 | Exact transform |
| XOR convolution, dimension 8 | Walsh-8 | Combine two input vectors |
| Inverse, dimension 8 | Walsh-8 | Solve the convolution system with kernel `(9,1,1,1,1,1,1,1)` |

The controller freezes these assets before generating its later public seeded inputs. Those tasks ask for a transform, a convolution and an inverse solution. They are new inputs within supplied mathematical interfaces, not new discovered scientific disciplines. The templates and objective remain human-supplied; the system cannot change its checker to declare progress.

The successor changes the required kernel to `(11,1,1,1,1,1,1,1)`. The old inverse remains valid for its original task but fails the new residual check. On the tested vector, its reconstructed first component is `-235/64` where the new requirement calls for `-3`. The new inverse reconstructs every requested component exactly. It becomes a seventh artifact while all six ancestors remain available. Runtime execution inherits Walsh-8; the inherited qualification path also uses the convolution capability as a reference. An all-ones singular kernel is rejected, retaining its 32 units of spent work.

This is capability compounding in a bounded sense: accepted executable structure expands the inventory of supported missions. It is not open-ended recursive invention or evidence that the resulting organization outperforms expert engineering.

### Workloads, budgets and the expert's wins

All numbers below use `paper-declared-arithmetic-work/v1`. Each round contains three tasks; every arm receives identical public inputs. Counts include applicable construction, current admission, productive arithmetic, independent reference arithmetic and output comparisons. [The retained result](../../evidence/thermal-witness-20261022/compounding-native-result.json) contains the individual receipts.

| Rounds | Tasks | Retain generated assets | Rebuild each round | Supplied static specialist |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 3 | 57,196 | 57,196 | 360 |
| 4 | 12 | 58,396 | 228,784 | 1,440 |
| 16 | 48 | 63,196 | 915,136 | 5,760 |

Retention saves 170,388 counted units at four rounds and 851,940 at sixteen against rebuilding. At a declared 60,000-unit allowance, retention completes twelve tasks while rebuilding does not; at 250,000 units, retention completes forty-eight while rebuilding does not. The specialist also fits those workloads and is cheaper. These are feasibility witnesses for supplied paths, not a search proving that no better path exists.

The specialist ties generated Walsh and convolution operating counts, at 24 and 88 arithmetic operations. Its fixed-kernel inverse uses 24 operations against the generated inverse's 64. Its exposed extra arithmetic preparation is zero; supplied authorship, proof and institutional qualification costs are unknown, not zero. No tested workload establishes an overall economic advantage over that expert alternative.

The predeclared relation is `retained = B + V + W(R)` versus `rebuilt = R(B + V) + W(R)`, where `B` is complete construction, `V` current admission and `W(R)` checked execution. Their difference is `(R−1)(B+V)`, which matched every workload. This is arithmetic amortization, not a monetary break-even forecast. The batches ran sequentially in one process; they do not measure concurrent capacity or service reliability under load.

### Authority, recovery and provenance

The existing [controller](../../examples/autonomous-enterprises/controller.mjs) uses the default charter with dimension reduced to eight: construction allowance 2,000,000, admission allowance 50,000,000, per-task allowance 2,000,000 and three tasks. These scoped work allowances are not cash budgets. Execution is `synthetic-local`; authority and obligations are empty. Reconciliation is `SIMULATED_ONLY`, currency `none`, collected cash `"0"`, and external submission `NOT_SUBMITTED`.

The journey constructs, freezes, commits tasks, reserves and reconciles execution, constructs the successor, then writes and reloads its completed workspace. Canonical contents and `SUCCESSOR_ACCEPTED_LOCAL` survive. This demonstrates completed-history recovery, not an operating-system crash during a pending invocation. Existing uncertain reservations require reconciliation; this probe adds no automatic retry permission.

Three recovery scopes remain distinct: the mathematical controller reopens its completed history; the thermal workbench imports inert evidence without authority; the native Python thermal runtime exercises signed-journal interruption and explicit resume. None establishes payment recovery or independent organizational approval. See the [thermal operating guide](../../examples/THERMAL_WITNESS.md) for the latter two paths.

Criteria were frozen before the first native evaluation. Independent source/data review found a receipt-label defect: specialist execution was incorrectly attributed to a generated artifact digest. A dated correction records `artifactDigest:null` and the actual specialist source; dispatch, criteria and counted costs did not change. Original source, protocol and result remain preserved. The corrected report is 935,180 bytes, SHA-256 `38867a8b9c593f91b2221c9828c3d260cfa50f26a2d390af8af85f4c9bfcf3f2`. The [review record](../../evidence/thermal-witness-20261022/compounding-review.json) reconciles both evaluations, 241 charge identities, all 104 corrected receipt hashes and 53 unchanged source-file identities. ## Layer 2 — a useful enterprise still needs a payer

The demonstrated value is avoiding unnecessary reconstruction while retaining applicability checks and history. Whether anyone should pay for that depends on their alternatives, demand, review burden and costs. The mathematical result already supplies a reason to choose the expert library for these fixed workloads. A competent centralized engineering team remains a required comparison.

A proposed voluntary pilot would ask a laboratory or process-development team to nominate a recurring decision that currently consumes scarce measurement or review capacity. That is a prospective role, not an identified customer. Before execution, the participant would specify the deliverable, acceptance uncertainty, permissible data/tools, workload, maximum resource commitments, ownership/licensing of reusable assets and what would justify another commission. A willingness-to-pay assumption stays an assumption until an actual authorized agreement exists.

Compare the existing expert workflow, a shared accepted-capability workflow, and rebuilding without reuse on the same tasks. Keep all training, rejected search, acquisition, calibration, validation, human intervention, maintenance, downtime and failed delivery costs. Record actual operator/reviewer effort and actual invoices in their currencies when available. Measure accepted decisions per scarce resource and changed-condition performance. Stop or revise if review overhead removes the gain, demand is insufficient, the expert alternative dominates, or measurement accuracy misses the decision need.

The reusable asset would be a licensed method, executable instrument definition and its evidence, not an automatic transfer of intellectual property or an incorporated business. Shared capacity would need explicit allocation among beneficiaries and available reviewers. More agent instances do not create instrument time, qualified validators, budgets or customers. No revenue, price, human-hour saving, token yield or staffing schedule is assumed here.

## Layer 3 — proposed physical progression

### Choose a construction that makes a limitation observable

| Direction | Productive mechanism | Present boundary |
| --- | --- | --- |
| Self-checking experimental interface | Add independently observed quantities and explicit uncertainty so a hidden error affects an inspectable result | Selected thermal source implementation; physical acquisition remains proposed |
| Discoverability compiler | Construct experiments that distinguish competing explanations before optimizing a process | Existing [#4872 owner lane](https://github.com/MontrealAI/AGI-Alpha-Agent-v0/pull/4872); this guide creates no competing compiler |
| Shared productive-capability foundry | Let voluntarily supported investigations reuse qualified instruments, methods and capacity | Long-term organizational target; demand, allocation and full cost must be demonstrated |

The thermal choice addresses the retained Foundry counterexample: the modeled runtime check passes at 4.9477% while true-heat error is 8.6964%. Commanded flow was used as a measurement. The new fixed adapter instead consumes a separate volume witness and bounded, volume-weighted differential temperature. Under its declared simulated assumptions, the retained mismatch produces a 1.8862% conservative error bound. That conditional numerical result preserves the original failure; it does not calibrate a real instrument.

The native adapter executes through the existing workbench and Python runtime. Three downstream families need different additional evidence: delivered heat needs complete flow and temperature coverage; sample heat capacity needs sample temperature rise plus losses and container storage; heat recovery needs input-energy and stored-energy-release bounds. Their instructions and failures are in [THERMAL_WITNESS](../../examples/THERMAL_WITNESS.md). The mathematical enterprise's current restricted-AST schema cannot accept thermal JSON as its seventh asset. That missing typed integration and independent promotion must be implemented through the existing owners.

### The next physical bench is a proposal

Begin with a bounded liquid-loop calorimetry bench: independently observed collected mass/volume, calibrated inlet/outlet temperature channels, synchronized acquisition, and an electrically metered reference with separately measured storage and losses. Specify the measurand, fluid/property range, operator-set limits and physical stop before collecting evidence. Use calibration and validation data separately. Inject flow-command error, sensor offsets, changed flow histories, missing intervals and property changes; preserve inconclusive and failed trials. A point temperature reading must not silently substitute for the required volume-weighted interval average.

NIST's [traceability policy](https://www.nist.gov/calibrations/traceability) places responsibility on the result provider to substantiate a documented calibration chain with uncertainty. Traceability alone does not establish fitness for the intended measurement. No project artifact or citation supplies that chain automatically.

[NIST TN 1297](https://www.nist.gov/pml/nist-technical-note-1297), a methodological reference, distinguishes uncertainty components and their combination, including relevant covariance, and requires an explained reporting basis. The adapter's deterministic bounds are not automatically statistical confidence intervals. A bench protocol must justify how its observations support those bounds or adopt an explicitly qualified uncertainty model.

Freeze physical acceptance criteria before decisive trials: reference containment under the declared measurement model, useful uncertainty for the nominated decision, deliberate fault detection, repeatability, changed-condition behavior and complete acquisition/review costs. Compare a conventional instrument with the same sensors and expert analysis; a tie remains valid. No bench has been purchased, commissioned or physically tested by this example.

### From software to useful physical output

Each proposed step below depends on evidence and resources from the previous step. The table is an engineering path, not a delivery forecast.

| Stage | Required capability and resources | Validation before reuse | Economic question |
| --- | --- | --- | --- |
| Digital | Existing checked programs, source bindings, compute and reviewers | Exact outputs, invalidation, recovery, complete work ledger | Does reuse beat the best available library after review? |
| Scientific instrument | Bench, calibrated sensors, reference apparatus, acquisition and operator time | Measurement uncertainty, drift, coverage, independent reference and fault trials | Is a decision cheaper or more reliable than with a conventional instrument? |
| Materials/process discovery | Samples, controlled environments, preparation equipment and experiment access | Distinguishable hypotheses, held-out conditions, reproducibility and durability | Does the resulting material/process improve a buyer's specified requirement? |
| Manufacturing | Production tooling, suppliers, inspection, operators and maintenance | Yield, batch variation, reproducible specifications and lifecycle failures | Do accepted units justify tooling, rejected batches and operating costs? |
| Infrastructure | Site engineering, installation, metering, controls and service capacity | Commissioning, availability, integration, maintainability and site acceptance | Does site-specific demand cover installation, outages and continued service? |
| Useful heat/energy | Matched source and use, transfer/storage equipment and independent meters | Useful delivery at the required temperature, net inputs, losses and degradation | Is there an actual beneficiary and a measured advantage after total costs? |

The DOE's [2015 waste-heat assessment](https://www.energy.gov/documents/qtr2015-6m-waste-heat-recoverypdf) identifies technical and economic limits on converting losses into useful recovery, including temperature, maintenance, material constraints and available end use. It is historical engineering context, not a current market valuation or evidence of this project's savings. Heat recovered without a useful destination is not automatically a saleable product.
